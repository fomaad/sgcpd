## 1. 目的

Autoware を実走（シミュレーション）させて得られたランタイムログを、既存の **CPD (Car Position Diagram) / GCPD** モデルと突き合わせ、次の2点を検証できるようにする。

1. **適合性検証（membership check）**：観測されたログの挙動が、CPDモデルが表現するシナリオ集合（`gcpd.py` の SAT/SMT 制約が許す `(car, box, lane, position, step)` の割当て空間）に含まれるか。
2. **性質の突合（property cross-check）**：CPDモデル上で成立する性質（衝突可能性など）と、ログから実際に観測される事象（衝突の有無、目標速度への到達など）が一致するか。

これは論文中で今後の課題として挙げられている「CPDモデルを具体的な地図・交通データと統合する」方向性の第一歩であり、CPDを**シナリオ生成**だけでなく**シナリオベース検証**（実行ログの適合性チェック）に使う拡張にあたる。

## 2. 入力データの整理

### 2.1 CPD/GCPDモデル（`gcpd.py`）

`Model` クラスが持つ要素（`sample1.py` より）:

| 要素 | 型 | 意味 |
|---|---|---|
| `cars` | `[str]` | 車両名のリスト（例: `"LCar"`, `"RCar"`） |
| `boxes` | `[(car, box_id)]` | 車両ごとの「箱」＝シナリオの離散状態 |
| `position` | `[(car, box_id, pos:int)]` | 箱の縦方向位置（整数の順序尺度） |
| `lane` | `[(car, box_id, lane:int)]` | 箱が属するレーン番号 |
| `inits` | `[(car, box_id)]` | 各車両の初期箱 |
| `ntrans` / `ctrans` / `netrans` / `cstrans` / `strans` | 遷移 | 通常・条件付き・非存在条件付き・カスタム条件・同期遷移 |
| `max_step` | `int` | シナリオの最大ステップ数 |

`Box(car_index, box_id, step): Bool` が「時刻stepにその箱がアクティブか」を表す一階述語で、`Pos`/`Lane` はその箱の位置・レーンを表す関数。**position と lane は連続座標ではなく、モデル設計者が与える離散的な順序値**である点が、ログとの対応付けで最も注意すべき点になる。

## 3. ギャップ分析

| | CPDモデル | Autowareログ |
|---|---|---|
| 空間 | `lane`（離散整数）・`position`（離散整数、順序尺度） | 連続座標 `x, y, z`（メートル） |
| 時間 | `step`（離散整数、0..max_step） | 連続時刻 `timestamp`（秒、~0.1s刻み） |
| 状態の存在 | 箱＝「その状態が成立している区間」を表す真偽値 `Box(c,n,s)` | 車両は常に存在し続ける連続軌跡 |
| 対象 | 抽象化されたシナリオの等価類 | 1回のシミュレーション実行の具体的トレース |

→ **ログを CPD のボキャブラリ（car, box, lane, position, step）に離散化する変換**が必要。この変換の設計が本ドキュメントの中心課題。

## 4. 提案するマッピング

### 4.1 車両の対応

- Autoware側 `ego` → CPD側 `"Ego"`（既存モデルでの `EgoCar` 系命名に合わせる）
- Autoware側 NPC（本データセットは基本 ego + NPC1台の想定）→ CPD側 `"RCar"` 等、検証対象のCPDモデルで使われている命名に合わせる

### 4.2 空間の離散化

- **lane**: サイドカーの `npc_lateral_m` を用い、egoレーンを `lane=0`、隣接レーンを符号に応じて `lane=1`（右）/`lane=-1`（左）のように量子化する。レーン境界（車線幅）は `jama_road_geometry=non_intersection` 前提のもと、AJISAI側のシミュレーション設定（`metadata`）から車線幅を取得して閾値化する。
- **position**: CPDのpositionは「箱の登場順」を表す順序尺度であり、メートル値そのものではない。したがって、`npc_longitudinal_m` や `delta_lateral_m` の**変化点**（イベント発生前後）を箱の切り替わり点として扱い、position はモデル定義側（検証対象のCPDモデル）にあらかじめ与えられている整数系列にそのまま対応させる。つまり「ログのどの時刻区間がモデルのどの箱に相当するか」を決める問題に帰着させる。

### 4.3 時間（step）の離散化

2方式を候補として提示する。

1. **イベント駆動（第一選択）**：サイドカーの `derivation.reference_frame_timestamp`（ラベル判定時刻）や、速度・横位置の変化が閾値を超えた時刻を「ステップの境界」とする。例えば cut_in なら `[割込み前（走行中）] → [割込み後]` の2ステップに対応し、`max_step=1` のモデルと対応させやすい。
2. **固定間隔（代替案）**：一定Δt（例: 1秒）ごとにサンプリングしてステップ列を作る。より忠実だが `max_step` が大きくなり、SAT制約も比例して増える。まずは方式1でPoCを行い、必要に応じて方式2に拡張する。

## 5. 検証の2モード

### 5.1 適合性検証（Conformance / Membership Check）

離散化して得た `(car, box, lane, position, step)` の割当てを、検証対象の `gcpd.Model` に対する追加制約として solver に投入し（`Box`/`Pos`/`Lane` の値を固定する等式制約を `add`）、モデル本来の制約（`add_pos`, `add_lane`, `add_init`, `add_trans`）と連立させて `solver.check()` を呼ぶ。

- **sat** → ログの挙動はモデルが表現するシナリオ集合の要素として矛盾なく説明できる（適合）。
- **unsat** → モデルが想定していない挙動（モデル外の振る舞い、またはモデルの不備、あるいは離散化の誤り）としてフラグを立てる。

### 5.2 性質の突合（Property Cross-check）

`gcpd.py` の `ps_col`（衝突述語）等を使い、CPDモデル上で「衝突が起こりうる」とされる箱の組と、ログ側で実際に観測される最小車間距離（`groundtruth_kinematic` から計算）やサイドカーの `consistency_ok` を突き合わせる。既にAJISAI側で行われている「filenameベースのラベル」対「trajectoryから導出したラベル」の整合性チェックと同様の考え方を、CPDモデル対ログの整合性チェックに応用する。

### 5.3 ラベルからモデルを自動選択

サイドカーの4軸ラベル（`jama_npc_position` / `jama_npc_direction` / `jama_npc_behavior`）を使い、どの既存CPDモデル（論文中のJAMA用モデル、または `experiment/` 配下のモデル）を検証対象として選ぶかを決めるルックアップテーブルを用意する。

## 6. 実装アーキテクチャ（提案）

`fomaad/sgcpd` 内に新規モジュール `logverify/` を追加する案。

```

├── jama_log.py     # 本体+サイドカーの読み込み → 内部表現 Instance に変換
```

- データセット本体（9.7GB）はリポジトリに含めず、外部パス／環境変数でBoxからの取得先ディレクトリを指定する運用とする。

## 9. 咲川論文に基づく具体化（v0.2）

### 9.1 咲川論文の要点

咲川氏の研究は、本ドキュメントが「4. ギャップ分析」で述べた「CPDの離散な語彙」と「Autowareログの連続な物理量」の間のギャップと**まったく同じ問題**（論文中では「抽象度のギャップ」）を、CPDとは独立に、抽象解釈（データマッピング）の枠組みで扱ったものである。提案されている2手法のうち、特に**車両周辺の領域分割（15領域モデル）**が本プロジェクトとの親和性が高い。

- **9領域モデル**: egoを中心に縦方向3分割（lead / ego / following）× 横方向3分割（left / ego車線 / right）＝9領域（lead-left, lead, lead-right, left, ego, right, follow-left, following, follow-right）。
- **15領域モデル**: 縦方向をさらに5分割（far-lead / lead / ego / follow / far-follow、閾値距離 `Dth = v_ego × 2.0s`）×横方向3分割＝15領域。9領域モデルより高い距離での接近予兆を捉えられ、実験ではFN=0を保ったままTNが改善（誤検知が減少）した。
- **時間の抽象化**：連続する同一の抽象状態を1つに集約するイベント駆動型の圧縮（本ドキュメントv0.1の「4.3 イベント駆動（第一選択）」で提案していたものと同一の考え方）。実データ（AWSIM）で平均状態数10個前後、圧縮率99%超を達成。
- **座標正規化**：ワールド座標系のego・NPC位置を、egoの進行方向を基準とした相対座標系へ回転変換する実装（`normalize_coordinates`）を持つ。これは本ドキュメントの「7. 未決事項 (4) 座標系」に対する具体的な答えを与える。
- **安全性の定義**：相対速度の符号＋領域（前方でPOS＝遠ざかる、後方でNEG＝遠ざかる、なら安全）による安全性判定を提案し、「抽象空間で安全と判定されたら具体空間でも安全」という健全性（over-approximation）を証明している（定理4.1相当）。実験でFN（危険の見逃し）= 0 を達成。
- **既知の限界**（論文7.4節）：(a) 蛇行（swerve）・Uターンのように「向き」の変化が本質的なシナリオは、位置ベースの領域分割だけでは検出できない。(b) 距離と速度を独立に抽象化しているため、安全性判定のFP（過検知）が多い。改善案として「述語抽象化」（例: `TTC<2.0` に相当する述語 `x - 2.0v < 0` を直接抽象状態に持たせる）を提案している。

### 9.2 CPDとの対応づけ（本ドキュメント4節の具体化）

咲川氏の15領域モデルの各シンボルは、**縦方向インデックス×横方向インデックス**の直積として素直に分解でき、これはCPDの `(lane, position)` とほぼそのまま対応する。

| 領域名 | lane（横方向） | position（縦方向、15領域） |
|---|---|---|
| far-left / lead-left / left / follow-left / far-rear-left | +1（左隣接車線） | far-lead=+2 / lead=+1 / ego=0 / follow=-1 / far-rear=-2 |
| far-front / lead / ego / following / far-rear | 0（自車線） | 同上 |
| far-right / lead-right / right / follow-right / far-rear-right | -1（右隣接車線） | 同上 |

（9領域モデルの場合は縦方向を {lead=+1, ego=0, following=-1} の3値に単純化すればよい。）

これにより、**咲川氏の抽象軌道 `T̂rj = ⟨ŝ'_0, ŝ'_1, …, ŝ'_m⟩` は、そのままCPDの箱列に変換できる**：

1. 各抽象状態 `ŝ'_k = (p̂_k, v̂_k)` の領域 `p̂_k` を上表で `(lane_k, position_k)` に変換する。
2. NPC車両について、CPDの箱を `("npc", k)`（`k = 0, …, m`）として生成し、`append_position([("npc", k, position_k)])`、`append_lane([("npc", k, lane_k)])` を登録する。
3. 連続する箱の間に通常遷移を追加する：`add_ntrans(("npc", k, "npc", k+1))`（すべての `k`）。
4. egoは自車中心の相対座標系の原点にあたるため、別途 `("ego", 0)` の固定箱として置くか、モデルの目的に応じて省略する。
5. `set_init([("npc", 0)])`、`max_step = m` として `Model` インスタンスを構成する。

この手順により、**1件のログから、そのログの挙動だけを表す「インスタンスCPDモデル」が機械的に生成できる**。これは咲川氏の「抽象化ツール」の出力形式（`follow-left → lead-left → lead` のような遷移系列）を、そのままCPDのモデル構築APIに流し込むアダプタに相当する。

### 9.3 適合性検証への接続（本ドキュメント5.1節の具体化）

「5.1 適合性検証」で述べた `check_membership` は、次のように具体化される。

1. **参照モデル**：JAMA行動セル（例: cut_in, ahead_right, same_direction）ごとに、許容される箱の遷移パターンを表す「参照CPDモデル」を用意する（`experiment/` にある論文Table Iのレーン変更モデルを参考に、`ntrans`/`ctrans` として「left→ego」「right→ego」等の遷移のみを許可する形で定義）。
2. **インスタンスモデル**：9.2節の手順で、検証したいログ（例: `TD-NI-AR-SD-N04-CI-0010`）から自動生成する。
3. **検証**：インスタンスモデルの `(box, lane, position, step)` 割当てを、参照モデルの制約（`add_pos`, `add_lane`, `add_init`, `add_trans`）に対する追加の等式制約として solver に投入し `check()` する。
   - **sat** → このログの挙動は参照モデルが定義する cut_in シナリオ集合の要素として矛盾なく説明できる。AJISAI側のサイドカーラベル（`jama_npc_behavior="cut_in"`, `consistency_ok=true`）との突合も行い、両者が一致するかを報告する。
   - **unsat** → 参照モデルが想定していない遷移（例：一度自車線に入ってからまた元の車線へ戻る、といった蛇行的な動き）が発生している。これは咲川論文が指摘した「swerve/u_turnを位置ベースの領域分割だけでは検出できない」という限界と表裏一体であり、**CPD側の視点では「参照モデルにない遷移＝新規シナリオ候補（unsat）として自動的に検出される」**という利点に転化できる可能性がある。

### 9.4 安全性判定への接続（本ドキュメント5.2節の具体化）

咲川氏の安全性定義（相対速度の符号＋領域）は、CPDの衝突述語 `ps_col(c1, c2, bx, t)`（同時刻に同じ `lane` かつ同じ `position` にいたら衝突）と両立する。咲川論文が課題として挙げた「距離と速度を独立に抽象化したことによるFP過多」は、まさに論文が提案する「述語抽象化」に相当するものをCPDが最初から備えている、と捉えることができる。すなわち、`Pos` と `Lane` を同時に扱う `ps_col` の条件式自体が、咲川論文で言う「距離と速度（正確には位置と位置）の結合条件」であるため、**CPDに衝突判定を委ねることで、咲川氏の手法単体よりもFPを抑制できる可能性がある**。この仮説はPoCで検証する価値がある。

## 10. cut-in の参照CPDモデルと格子ベース抽象化（v0.3）

### 10.1 動機：なぜ咲川氏の名前付き領域ではなく格子ベースにするのか

第9節までの `cpd_bridge.py` は、咲川氏の15領域抽象化ツールの出力（`lead-right`, `far-front` のような領域名の列）を、`REGION_TO_LANE_POS` という固定のルックアップ表で `(lane, position)` に変換していた。この方式は「1本のログを要約し、そのログ専用のインスタンスCPDを作る」用途には向いているが、次の点で「cut-inというシナリオ集合そのものを表す参照CPD」を**自分たちで直接書き下す**用途には合わない。

- 15領域モデルの境界（`Dth = v_ego × 2.0s` など）は、咲川氏が別の目的（安全性判定）のために選んだ閾値であり、参照CPDを設計する際にこちらが選びたい粒度（例えば「1箱=5m」）とは独立に決まってしまっている。
- 領域名は9〜15種類の固定カテゴリしかなく、参照CPD側で「隣接レーンのどこから出発してもよい」といった**任意の範囲**を表現しようとすると、結局は領域名を経由せずに `(lane, position)` を直接扱いたくなる。

そこで、**参照CPDを設計するときに使う格子のセルサイズ (gx, gy) を先に決め、ログの離散化にも同じ (gx, gy) を使う**、という順番に変更する。ログのどの時刻についても `position = round(rx/gx)`, `lane = round(ry/gy)` という整数がそのまま得られ（`logverify/grid_bridge.py`）、これは参照CPDモデルの `(lane, position)` の語彙と最初から一致する。咲川氏の抽象化との違いは「固定の意味的カテゴリ」対「設計者が選ぶ物差しの目盛り」であり、後者の方が参照CPDの直接記述と相性が良い。

なお、咲川氏の `vendor/trajectory_abstraction/src/abstraction_grid.py` / `safe_grid.py` も内部的に格子ベースの抽象化を実装済みだが、境界が `floor(ry/gy)` で `k=0` が `[0, gy)` と非対称になっている（自車線中心 `ry=0` を跨がない）。`logverify/grid_bridge.py` では `round()` ベースの対称な離散化（`k=0` が `[-gy/2, +gy/2)`）に変更し、「lane=0 は自車線」という直感と一致させている。

### 10.2 cut-in の参照CPDモデル（`logverify/reference_models.py`）

`build_cutin_reference(i_range, side_lanes=(-1,1), ego_lane=0)` が、次の形の `gcpd.Model` を機械的に生成する。

1. **状態空間**：`side_lanes ∪ {ego_lane}` の各レーンと、`i_range` の各縦方向位置の直積を、それぞれ1つの箱として列挙する（`i_range` を広く取るほど、扱える縦方向レンジが広がる）。
2. **隣接レーン内の移動**：レーンを跨がずに `position` が ±1 だけ変わる遷移（接近・離反）。
3. **合流（cut-inの核心）**：隣接レーンから `ego_lane` へ、`position` が高々1変化して移る遷移。
4. **合流後**：`ego_lane` 内でのみ `position` が変化できる。**隣接レーンへ戻る遷移は一切定義しない。**
5. **非決定的な出発点**：実座標を持たないダミーの開始箱（`START_BOX`）を1つ用意し、そこから隣接レーンの任意の箱へ遷移できるようにする。こうすることで「隣接レーンのどこから出発してもよい」「左右どちらの隣接レーンから来てもよい」という非決定性を、`gcpd.Model` が前提とする「各車について常にちょうど1つの箱がアクティブ」という不変条件を壊さずに表現できる（詳細はモジュール内のコメントを参照）。

4番目の制約が「カットイン」と「蛇行(swerve)」を区別する核である。一度合流したあとに元のレーンへ戻る、あるいは往復するようなトラジェクトリは、対応する遷移が存在しないため、この参照モデルでは構造的に受理されない。

### 10.3 適合性検証（`logverify/membership.py`）

`check_membership_cutin(model, observed)` は、観測された `(lane, position)` の列（`logverify/grid_bridge.py` が出力する圧縮済みグリッド状態列からそのまま作れる）を、参照モデル自身の制約（`add_pos`, `add_lane`, `add_init`, `add_trans`）に対する追加の等式制約として solver に投入し、`solver.check()` を呼ぶ（5.1節・9.3節で述べた方式の実装）。

- **観測の各ステップ** t について「その `(lane, position)` を持つ箱のどれかがアクティブ」という論理和制約を追加する（該当する箱が1つも無ければ、その時点で構造的にUNSATと確定する）。
- ダミー開始箱の分、観測列の先頭はモデルの step 1 に対応する（`start_offset=1`）。
- `gcpd.py` はモジュールレベルの可変な `solver`/`c2i` を持つため、`check_membership` は呼び出しのたびに明示的にリセットする（`reset_solver()`）。

`logverify/demo_cutin_membership.py` で、実データが手元になくても検証できる3種類の合成トラジェクトリ（典型的なcut-in／最初からego車線／合流後に元のレーンへ戻る蛇行）に対してこのパイプラインを流し、期待通り SAT / UNSAT / UNSAT が得られることを確認済みである。

```
$ python3 -m logverify.demo_cutin_membership
cutin_like        : SAT
stays_in_own_lane : UNSAT
swerve_like       : UNSAT
```

### 10.4 未検証・今後の課題

1. **実データでの検証**：本節のパイプラインは合成トラジェクトリでのみ検証済みであり、AJISAIの実ログ（cut_in 94件）に対してはまだ流していない。`logverify/grid_bridge.py` の `grid_states_from_json(path, gx, gy)` はAJISAIの `<id>.json`（`groundtruth_kinematic`）にそのまま使える設計だが、外部（Box）からデータセットを取得できる環境で実行する必要がある。
2. **セルサイズ (gx, gy) の選び方**：本節のデモでは `gx=5.0m, gy=3.5m`（車線幅相当）を暫定的に使ったが、これがAJISAIの実データに対して適切か（粗すぎて別々の状態を同一視してしまわないか、細かすぎて `i_range` が発散しないか）はPoCで確認する必要がある。咲川論文・`safe_grid.py` が実験しているセルサイズの候補（`(1.0,1.0), (1.75,1.75), (3.5,3.5)` 等）を横展開して比較するとよい。
3. **cut_out・deceleration との切り分け**：本節の参照モデルは「隣接レーン→egoレーン」の合流のみを許すため、cut_out（逆方向）や lane change を伴わない加減速シナリオは自動的にUNSATになる（＝別の参照モデルが必要、という結果自体は意図通り）。cut_out用の参照モデル（`ego_lane`→隣接レーンの合流のみ許す、対称な定義）を同様に用意し、`jama_npc_behavior` ラベルとの一致率を集計するのが次の一歩になる。
4. **咲川氏の安全性判定との統合**：9.4節で述べた `ps_col`（CPDの衝突述語）による突き合わせは、本節の格子ベースの参照モデルに対してもそのまま適用できるはずであり、まだ試していない。
5. **蛇行(swerve)の扱いの一般化**：本節のUNSAT判定は「一度合流したら戻れない」という単一の制約に基づく。実際のswerveはもっと多様なパターン（合流せずに近づいたり離れたりを繰り返す等）を含みうるため、`side_lanes` 内の往復も含めて「何が蛇行としてUNSATになるべきか」をAJISAIのswerveラベル（130件）で確認し、必要なら参照モデルをさらに洗練する。

### 10.5 距離帯・並走・加速のバリエーションを1つのモデルに統合する（v0.4）

10.2節の初版は `i_range` を生の格子インデックス（例えば0〜19の20値）でそのまま箱にしていたため、近距離・中距離・遠距離それぞれで始まるcut-in、あるいは隣接レーンでしばらく並走してから加速して合流するcut-inを扱おうとすると、`i_range` を広げる必要があった。しかし箱の数は `|lanes| × |i_range|` で増え、遷移（隣接レーン内・合流・ego車線内）を総当たりで張ると箱数の2乗のオーダーで増えるため、`i_range` を広げるとソルバが実用的な時間で終わらなくなることが分かった（20値程度で2分のタイムアウトに達した）。

これは「CPDのpositionは連続座標ではなく順序尺度である」という2.1節の指摘を、参照CPDの設計そのものにも適用すべきだったということである。そこで `logverify/zones.py` を追加し、縦方向の距離 `rx` を「後方(-1) / 近距離(0) / 中距離(1) / 遠距離(2)」という4値の順序尺度に丸めてから箱を作るようにした（`reference_models.build_cutin_reference` のデフォルトの `i_range` もこの4値になった）。これにより：

- 箱の数は距離レンジによらず一定（`|lanes| × 4`）になり、ソルバは瞬時に終わる。
- 「近距離cut-in」「中距離cut-in」「遠距離cut-in」「隣接レーンで並走してから加速して合流するcut-in」は、いずれも**同じ1つの参照CPD**（`build_cutin_reference()` の1回の呼び出し）に対する、それぞれ異なるSATの充足解（witness）として表現される。これがCPDの強み（「バリエーションを1つのモデルで書ける」）を実際に確認できた点である。
- `logverify/report.py` の `summarize_trace` / `describe_scenario` が、SATと判定されたログの `(lane, position=zone)` の系列を、実際にどの距離帯から出発し、どこで並走したとみられ、どこで合流したかという日本語の要約に変換する（並走の判定は、圧縮済み状態の継続フレーム数がしきい値以上かどうかで行う。position自体は既に距離帯に丸められているため、「同じ距離帯の状態が何個続くか」ではなく「1状態がどれだけ長く継続したか」で判定する必要がある点に注意）。

`logverify/demo_cutin_membership.py` で、近距離・中距離・遠距離・並走+加速の4種類のcut-inと、2種類の負例（ego車線に留まり続ける／蛇行）を同じ参照モデルに対して判定し、期待通りの結果（前者4つはSAT、後者2つはUNSAT）を得ている。

今後の課題として、10.4節の内容に加えて次を追加する。

6. **距離帯のしきい値 (`ZoneThresholds`) の妥当性**：本節では `near_max=5m, medium_max=20m` を暫定的に使ったが、AJISAIの実データにおける典型的なcut-in開始距離の分布を見て調整する必要がある。
7. **「並走」判定のしきい値**：`parallel_min_frames`（継続フレーム数）は暫定値であり、実データのサンプリング間隔（約0.1秒）を踏まえて、何秒以上の並走を「並走」とみなすかを再検討する。

## 11. ログからCPDを構築する3つの方法（v0.4）

ここまでで、ログからCPDを構築・利用する方法が複数出てきた。それぞれ目的が異なるため、どれか1つに統合するのではなく、**3つの独立した方法として`logverify/`（および`vendor/`）に併存させる**方針とする。

**咲川氏のvendorコードへの依存について**: 方法B・方法C（`logverify/`配下）は、咲川氏の`vendor/trajectory_abstraction/`配下のコードには一切依存せず、独立に実装している。咲川氏のコードを使うのは方法A（`vendor/trajectory_abstraction/src/cpd_bridge.py`）のみである。なお、実装の初期段階で`logverify/grid_bridge.py`に咲川氏の座標正規化関数（`normalize_coordinates`等）を再利用する`grid_states_from_json`関数を用意していたが、実際にはどの方法でも使われておらず（合成トラジェクトリでのテストに留まっていたため）、方法B・Cをvendorコードから完全に独立させる方針のもと削除した。実データ（AJISAIログJSON）からego基準の相対座標を取り出す部分が必要になった際は、`logverify/`内で独立に実装する。

| | 方法A（既存） | 方法B | 方法C |
|---|---|---|---|
| 実装 | `vendor/trajectory_abstraction/src/cpd_bridge.py`（第9節） | `logverify/reference_models.py` + `logverify/zones.py`（第10節） | `logverify/multi_log_model.py`（本節） |
| 入力 | ログ1本 | 「シナリオ集合」の定義（設計者が手で書く） + 検証したいログ | ログN本（複数） |
| 出力 | そのログ専用の「インスタンスCPD」 | 参照CPD（cut-inなど）と、ログがそれに適合するか(SAT/UNSAT) | N本のログをまとめて表す「統合CPD」 |
| 抽象化の単位 | 咲川氏の名前付き領域（9/15領域） | 距離帯（近距離/中距離/遠距離、順序尺度） | 生の格子（ログを区別できる最小の細かさまで自動的に細かくする） |
| 主な用途 | 1本のログを要約・可視化する | 「これはcut-inか？」を判定し、どの距離帯・並走の有無かを分類する | 複数の実例から、それらを包含するシナリオ集合を機械的に構築する |

### 11.1 方法C：複数ログの統合CPD構築

ご相談の「複数のログがあったときに、それを1つのCPDとしてモデル化する」方法である。方針は次の通り。

1. **格子の自動選定**：`multi_log_model.find_distinguishing_grid` が、粗い格子（デフォルト `gx=5.0m, gy=3.5m`）から始めて、**全てのログが互いに異なる箱列に離散化されるまで**格子を半分ずつ細かくしていく。2本のログが物理的には別々の挙動でも、粗い格子では同じ箱列に潰れてしまうことがあるため（実際、`gx=5.0, gy=3.5` で区別できなかった例を確認済み）、常に「今与えられたログ集合を区別するのに十分なだけ」の細かさを自動的に選ぶ。
2. **統合モデルの構築**：`multi_log_model.build_union_model` が、各ログの箱列（(lane, position)の系列）を、1つの`gcpd.Model`の中の「そのログが辿った経路」として書き込む。複数のログが同じ箱を通れば、そこでモデルの中の経路が自然に合流する。実座標を持たないダミーの開始箱（`START_BOX`）を使い、「どのログの出発点から始まってもよい」という非決定性を、方法Bと同じ仕組みで表現する（10.2節参照）。
3. **含意の確認**：`multi_log_model.verify_logs_included` が、統合モデルに対して各ログの箱列がmembership check（第10.3節と同じ仕組み）でSATになることを確認する。
4. **シナリオ列挙による検証**：`multi_log_model.count_scenarios` / `enumerate_scenarios` が `gcpd.s_count` / `gcpd.enum_ss`（3節・9.6節でも使っている、CPDの標準的なシナリオ列挙機能）をそのまま呼び出し、統合モデルから実際に列挙されるシナリオの総数と中身を返す。**列挙されたシナリオ数が入力したログの本数と一致すれば「一般化なしでログがそのまま再現された」ことを、それより多ければ「複数のログの部分列が組み合わさり、入力にはなかった新しい経路も生成された」ことを意味する**。後者はまさにCPDが持つ「具体例の集合から、それらを包含する一般化されたシナリオ集合を作る」という能力の現れである。

`logverify/demo_multi_log_model.py` で、4本の合成ログ（右隣接レーン近距離/遠距離からのcut-in、左隣接レーンからのcut-in、自車線に留まり続けるログ）を統合し、期待通り4本すべてがSATで含まれ、シナリオ列挙数も4（＝この例では偶然どのログも他のログと箱を共有しなかったため一般化は起きなかった）であることを確認した。また、2本のログが粗い格子では同一の箱列に潰れてしまう例を作り、格子の自動細分化によって正しく区別されることも確認した。

### 11.2 未検証・今後の課題（方法C）

1. **実データ10本での検証**：ご相談にあった「10個のログを区別できる格子で1つのCPDにする」を、実際のAJISAI cut_inログ10本程度で試す。ログ本数が増えると、格子をどこまで細かくすれば全てを区別できるかが非自明になる可能性がある（`find_distinguishing_grid`の`max_iters`で頭打ちになるケースを実データで確認する）。**11.6節で合成ログ19本による大規模化の予備実験は行ったが、実データでの検証はまだ未着手のまま残っている。**
2. **意図した一般化と意図しない一般化の区別**：統合モデルが入力より多くのシナリオを生成した場合、それが「望ましい一般化」（例：cut-inのタイミングだけが違う2本のログが、共通の合流点を経由することで自然に組み合わさる）なのか、「格子が粗すぎたことによる意図しない混線」なのかを区別する基準が必要。方法Bの距離帯（順序尺度）の考え方を方法Cにも取り入れ、「区別すべきものは区別し、区別しなくてよいものは積極的にまとめる」バランスを取ることが次の課題になる。**11.7節で、Egoに近い部分は細かく・遠い部分はまとめる非一様格子（`build_union_model_near_far_grid`）という第一歩を実装した。ただしこれは「Egoからの距離だけ」に基づく単純な切り方であり、「望ましい一般化かどうか」を判定する基準そのものはまだない。**
3. **方法A・Bとの接続**：方法Cで作った統合CPDに対して、方法Bの参照CPD（cut-inの一般形）との関係を調べる（統合CPDのシナリオが、方法Bの参照CPDのmembership checkをすべて通るか、など）。

### 11.5 Egoが前進するワールド座標系でのアニメーション

#### v1（初版、可視化側だけの後付け）

11.3節のGIFは、モデルが持つ`(lane, position)`をそのまま「ego基準の相対座標」の格子とみなし、egoを`lane=0, position=0`に静止させて描いていた。しかし実際にはegoも道路上を前進しており、positionが変化しないのは「NPCとの相対距離」を状態として使っているからに過ぎない。論文的な見た目にする際、egoも動いているように見せたいという要望を受け、`logverify/world_frame_gif.py`の初版では、Egoが一定速度で前進すると仮定し（`ego_world_position(step) = step × ego_speed`）、NPCの絶対位置を`ego_world_position(step) + モデルが持つ相対position`として可視化側だけで計算していた。

これに対し「オリジナルの英語の論文では、CPDでEgoが動いているようにモデル化しているはず」という指摘を受けた。論文（Fig.2/Fig.7）を確認すると、確かにEgoも他の車（LCar, RCarなど）と同じく1つの car として、"positionは箱の並び順そのもの"という規約（concrete box、論文IV-C節）に基づく箱列を持つ形でモデル化されている。v1はCPDモデル自体にはEgoという car が存在せず、可視化側だけの後付け計算に留まっていたため、この指摘は正しい。

#### v2（Egoを実際にCPDの car として追加）

`logverify/ego_car.py`の`with_ego_track`を追加し、Egoを実際にCPDの car として追加したモデルを構築するようにした（`logverify/world_frame_gif.py`はv2としてこれを使うよう全面的に書き直した）。

素朴には「Ego(0)->Ego(1)->...->Ego(max_step)という独立した箱列をNPCと同じモデルに追加するだけ」で良さそうに思えるが、これはうまくいかない。gcpd.py の`add_trans`は、1ステップにつき「登録されている遷移のうちどれか1つだけが発火する（＝1台の車だけが箱を変える）か、何も起きないか」という排他的選択を各ステップに課している（sample2.pyのLCar/RCarのように、2台が独立に「互いに異なるステップで」進むことは表現できるが、「2台が同じステップで同時に進む」ことは表現できない）。そのため、Egoに独立した箱列を追加しただけだと、EgoとNPCは同じステップ予算を奪い合う「独立に進む2台の車」になってしまい、Egoが毎回確実に前進する保証がなくなる（NPCの遷移が選ばれた回数のぶんだけEgoは足止めされる）。

そこで、論文の定義3で正式に定義されている**同期遷移（Es、gcpd.pyでは`strans`）**を使った。これはFig.8のblind spot事例で「青い車が車線変更すると同時に赤い車も動く」という記述に対応する、CPD本来の機構である。NPC側の全ての通常遷移（各距離帯・車線間の遷移）それぞれに対して、「そのNPCの遷移が発火するときは、Egoの箱列も同時に1つ進む」という同期遷移グループを機械的に生成し、NPC側の元の通常遷移は（単独では発火できないよう）この同期版に置き換える。これにより、

- NPCが実際に距離帯・車線を変える瞬間には、必ずEgoも1つ前進する。
- NPCが変化しないステップでは、Egoも変化しない（「何も起きないステップ」として扱われる）。
- Egoの経路は常に一本道（Ego(0)->Ego(1)->...）なので、これによってNPC側の充足解の集合が変わることはない（`logverify/demo_world_frame_gif.py`で方法Cの4本の合成ログについて確認したところ、Egoを追加する前後でシナリオ数が4のまま変わらないことを確認した）。

というEgoの前進が、CPDが表現するシナリオの一部として（可視化のための後付けではなく）solverが解いた結果そのものとして得られるようになった。

NPC側の position は（方法B・Cとも）Egoとの相対距離をそのまま表しているため、1枚の固定カメラの絵として描画する際には、`NPCの絶対position = Ego(box).position（=これまでの同期前進の回数） + NPCの相対position`として画面上の座標に変換する（この変換自体は見た目のためのもので、CPDが表現するシナリオ集合の意味＝相対距離ベースを変えるものではない）。lane（横方向）はもともとego基準の相対値（隣接レーン=-1/1など）なので変換不要で、そのまま「egoからの左右オフセット」として使う。カメラはワールド座標系に固定（egoを追従しない）。

- 方法Bの参照CPDは非決定性が大きく全列挙が膨大になりうるため、可視化用には`num_model`で列挙数を絞れるようにした（`logverify/demo_world_frame_gif.py`では代表6シナリオに絞っている）。方法Cの統合モデルはログ本数が確定しているため通常はそのまま全列挙してよい。
- `ego_speed`（Egoの箱番号を画面上の格子セル数に変換するスケール）の意味合いは、相対distanceが順序尺度（距離帯）である方法Bと、実際の格子（メートル単位）である方法Cとで厳密には異なる点には注意が必要。Egoの絶対速度自体はログの相対座標だけからは復元できない情報であり、あくまで見た目のためのパラメータである。
- 本節の同期は`model.ntrans`（通常遷移）のみを対象としている。現状の方法B・Cのモデルはntransしか使っていないため問題にならないが、将来`ctrans`/`netrans`等を使うモデルにEgoを追加する場合は`ego_car.py`の拡張が必要になる。

今後の課題として、`ego_speed`を実データ（AJISAIログの座標変換前の絶対座標、あれば）から推定し、より物理的に正確なアニメーションにすることが挙げられる。

#### 描画上の注意: 距離帯（順序尺度）をそのまま座標に足すと衝突に見える

v2のアニメーションを実際に見たところ、cut-in参照CPD（方法B）でNPCがEgoと完全に重なって「衝突しているように見える」場面があった。原因は、方法Bのpositionが`logverify/zones.py`の BEHIND=-1 / NEAR=0 / MEDIUM=1 / FAR=2 という**順序尺度の距離帯カテゴリ**であり、実際のメートル距離ではないことにある。「NPCの絶対position = Egoの絶対position + NPCの相対position」という変換式にNEAR=0をそのまま代入すると、数値としてはEgoの座標にちょうど0を足すことになり、Egoとまったく同じ格子セルに描画されてしまう。これはモデルが「衝突するシナリオ」を表しているわけではなく、「近い」という抽象的な分類がたまたま0という数値で表現されていたことによる、レンダリング上のアーティファクトである（衝突可能性の判定自体は9.4節の`ps_col`と組み合わせる別の話であり、本節の参照CPDにはまだ組み込んでいない）。

対策として、`render_world_frame_gif`に`zone_ahead_offset`引数を追加した。0以上（Ego手前ではない側＝NEAR/MEDIUM/FAR）の距離帯にだけ一律のオフセットを足すことで、NEARがEgoとちょうど同じセルに重ならないようにする（BEHINDは既に負の値でEgoより手前と区別がついているため対象外）。方法Bを描画する際は`zone_ahead_offset=1`以上を指定する。方法C（positionが実際の格子＝メートル単位）では、0が本当に「ほぼ同じ位置」を意味しうるため、デフォルトの0（オフセットなし）のままにしておく。

#### 描画上の注意（続き）: 車線変更の直線補間・車の描画サイズ

上記の修正後も、「NPCが上からEgoに重なって下に移動しているように見える＝衝突しているのでは」という指摘を受けた。実際にGIFのピクセルを追跡して確認したところ、レーン変更を伴う遷移で本当に矩形が重なっているフレームが複数あった。原因は2つあった。

1. **車線変更の直線補間**: (旧レーン, 旧position)から(新レーン, 新position)へ愚直に直線で補間すると、横方向(レーン)と縦方向(position)が同時に動くため、斜めに突っ切る軌跡がEgoの位置をかすめることがある。参照CPDの`max_position_jump`を1に制限しても（距離帯を1段ずつしか変えられないようにしても）、レーン変更自体は起きるため、この現象は解消しなかった。根本的な対策として、レーン変更を伴う遷移では「まず現在のレーンのままposition だけ動き、その後にレーンだけを切り替える」という2段階の中間フレームを挿入するよう`render_world_frame_gif`を変更した（実際の車線変更＝縦に詰めてから横に合流する、という一般的な運転動作にも近い）。これはCPDが検証した状態そのものは変えず、描画上の補間経路を分割するだけである。
2. **車の描画サイズがセル幅を超えていた**: `gcpd_gif.VehicleGif`のデフォルトの車の矩形幅（100px）が、本アニメーションで使っていた1セルの幅（`grid_scale=120px`）に対してmarginと合わせると収まりきらず、**隣接するレーンの車同士が、実際にはレーンが違うのに矩形が視覚的に重なって**しまっていた。車の幅・高さをセル幅に収まるよう縮小し、marginもそれに合わせて調整した。

修正の効果をピクセル単位で検証したところ（`world_cutin.gif`で赤と青の矩形のbounding boxが実際に重なっているフレーム数をカウント）、修正前は15回の重なりがあったのに対し、修正後は0回になった。なお、NPCがEgoと同じレーン・同じ距離帯（NEAR）まで実際に近づく場面自体は今後も起こりうる（それ自体はモデルが表現している通りの状態であり、隠すべきものではない）。今回直したのは、モデルが表現していないはずの中間軌跡や、レーンが違うのに重なって見えるという、純粋な描画上の誤りである。

#### モデル構造図へのEgoの反映

11.4節の`plot_model_paper_style`はNPC側のスイムレーンしか描かないため、Egoが実際にCPDの car として存在することを図でも確認できるよう、`logverify/model_diagram.py`に`plot_model_with_ego_paper_style`を追加した。NPC側のスイムレーンの上に、Egoの箱列（Ego(0)->Ego(1)->...）を緑色の帯で追加している。同期遷移（strans）は「NPCのntrans1本ごとにEgoの箱番号すべてとの組」を機械的に生成しており、実際の組み合わせ数は膨大（`|ntrans| × ego_max_step`）になるため、1本ずつ線で結ぶと図が読めなくなる。そのため、同期の事実は図中の注記テキストで示すに留めている。`logverify/demo_model_diagram_with_ego.py`で方法B・方法Cの両方について生成・確認した。

### 11.6 方法Cの大規模化（合成ログ19本）

11.1節の確認は合成ログ4本のみで行っており、しかも4本はどれも縦方向（rx）の範囲が互いに重ならないように選んであったため、格子の自動細分化がほとんど試されていなかった。「今は4本しか使っていないが、もう少し大きい規模の実験ができるか」という要望を受け、`logverify/demo_multi_log_model_large.py`を追加し、方法Cのみを対象に規模を広げた実験を行った。

**入力ログの構成（合成、19本）**：右隣接レーンからのcut-in（近距離/中距離/遠距離×各2本）、左隣接レーンからのcut-in（近距離2本＋中距離・遠距離各1本）、自車線に留まり続けるログ（3本、あえて他のcut-inログとrxの範囲を重複させている）、隣接レーンで並走してから合流するログ（左右各1本）、一度合流してから再び隣接レーンへ抜けるcut-in+cut-outログ（左右各1本）、蛇行(swerve)のようなログ（2本）、の8カテゴリを組み合わせた。4本のときと異なり、rxの範囲を意図的に重複させたログを複数含めている点が格子選定への負荷を高めている。

**結果**：

- 格子の自動選定はデフォルトの`gx=5.0, gy=3.5`のまま（細分化の反復なし）で19本すべてを区別でき、格子選定＋統合モデル構築は数秒未満で完了した。19本程度・このような合成ログの多様性であれば、デフォルトの粗い格子でも十分に区別できることが分かった。
- 統合モデルの箱数は33（ダミー開始箱を含む）、`max_step=6`。
- membership check（19本全てが統合モデルに含まれるかの確認）は31.03秒で完了し、19本全てSATであることを確認した。
- シナリオ列挙数は29（入力19本より10多い）。4本のときはシナリオ数が入力本数と一致し一般化が起きなかったが、rxの範囲を意図的に重複させたことで、複数ログが箱列の一部を共有し、入力にはなかった経路が10本追加で生成された。これは11.2節の課題2「意図した一般化と意図しない一般化の区別」に直接関わる観察であり、格子・ログの与え方次第で一般化の起き方が変わることが具体的に確認できた（どの追加経路が「望ましい一般化」でどれが「意図しない混線」かの評価は今後の課題のまま）。
- モデル構造図（`plot_model_with_ego_paper_style`、11.5節）はこの規模でも問題なく描画できた（`model_multilog_large_with_ego.png`）。
- 一方、Egoを同期遷移（strans）で実際にCPDのcarとして追加したワールド座標系アニメーション（11.5節のv2、`with_ego_track`ベース）は、この規模（33箱、`max_step=6`）では同期遷移グループの組み合わせ数（NPCの通常遷移数×Egoの`max_step`）が膨れ上がり、480秒経っても計算が終わらなかった。そのため大規模デモでは、Egoを同期させない単純な静止Ego版（11.3節の`gif_viz.py`、`render_scenarios_gif`）にフォールバックしたところ97.19秒で描画できた（`multilog_large.gif`）。この点は11.7節で解消した（詳細はそちらを参照）。

以上より、方法Cのモデル構築・membership check・シナリオ列挙といった検証の中核部分は19本規模でも実用的な時間で動作することを確認できた。ただし本節の実験はいずれも合成データであり、実データ（AJISAIログ）による検証は11.2節の課題1として引き続き残っている。

### 11.7 大規模モデルでのアニメーション高速化：全列挙をやめる／格子を非一様にする

11.6節でEgoを同期させたワールド座標系アニメーションが19本規模でタイムアウトした件について、2つの指摘を受け、それぞれ対策を実装・検証した。

**(1) そもそも全シナリオを列挙する必要はない**。`check_membership`（本節冒頭、membership.py）を見直すと、「ログが統合CPDに含まれるか」の検証は、統合CPD自身の制約とログの箱列の制約を1つのsolverに投入し、`solver.check()`を**1回だけ**呼んでSAT/UNSATを見ているだけで、`gcpd.enum_ss`のような解の列挙は元々使っていない。19本のmembership check（31秒）もEgoなしでこの方式のまま高速に動いている。一方、アニメーションで`enum_ss`を使っていたのは「絵として見せるための具体的なシナリオを何本か取り出す」ためであり、検証のためではない。そこで`render_world_frame_gif`の`num_model`（列挙するシナリオ数の上限）を、可視化に必要な数個（実験では5）に絞ったところ、19本規模のモデルでも約19〜30秒で描画が完了することを確認した（`num_model=3`で22.6秒、`5`で30.3秒、`8`で41.6秒、と列挙数にほぼ比例して増加する一方、`num_model`を小さく保つ限り実用的な時間に収まる）。

**(2) 格子の設計を、Egoに近い部分は細かく・遠い部分はまとめる非一様なものに変える**。11.1節の格子は、Egoからの距離(rx)・レーン(ry)いずれについても一様なセルサイズを使っていた。しかし「Egoに近い部分の挙動は詳しく区別する必要があるが、遠い部分は多少まとめてしまってよい」という考え方（まさに方法Bの距離帯＝順序尺度の発想であり、11.2節の課題2「方法Bの距離帯の考え方を方法Cにも取り入れる」の第一歩にあたる）に基づき、`grid_bridge.grid_index_variable`と`multi_log_model.build_union_model_near_far_grid`を追加した。`|rx| <= rx_near_range`の範囲は従来通りのセルサイズ（実験では5m）で細かく量子化し、それを超える範囲はより粗いセルサイズ（実験では10m）でまとめる。19本のログに対して`rx_near_range=45m`（後述の理由でこの値を選んだ）、遠方セル10mで試したところ、

- 箱数：33 → 28
- max_step：6 → 5
- membership check：19/19 SAT（31.83秒 → 20.58秒）
- シナリオ列挙数：29（一様格子と同じ、生成された一般化の本数は変わらなかった）

と、モデルのサイズを縮小しつつ、検証結果自体（含意関係・一般化の起き方）は変わらないことを確認した。`rx_near_range`は機械的に決めたものではなく、今回の合成ログの「中距離」カテゴリ（rx=20付近から始まる）が遠方セルとの境界をまたいで区別できなくなる（`cutin_right_medium_1`と`_2`などが同じ箱列に潰れる）ことを実際に確認しながら、それを避けられる値（45m）まで広げて選んだ。つまり、非一様格子は自動細分化（`find_distinguishing_grid`）とは独立の仕組みであり、`rx_near_range`・遠方セルサイズの選び方によっては区別すべきログ同士が潰れてしまう可能性があるため、`build_union_model_near_far_grid`は`find_distinguishing_grid`のような自動探索は行わず、呼び出し側が指定した値をそのまま使う（区別できているかは`sequences`の重複チェックで別途確認する必要がある）。

**(1)(2)を組み合わせた結果**：非一様格子のモデル（28箱、max_step=5）に対して`num_model=5`でEgoを同期させたワールド座標系アニメーションを生成したところ、19.03秒で完了した（`multilog_large_with_ego.gif`、対応するモデル構造図は`model_multilog_large_near_far_with_ego.png`）。11.6節で480秒経っても終わらなかったのと同じ規模のログ集合に対して、Egoを実際にCPDのcarとして同期させた「論文と同じモデル化」でのアニメーションが実用的な時間で得られるようになった。

なお、`build_union_model`（一様格子）と`build_union_model_near_far_grid`（非一様格子）は、どちらも方法Cの実装として`logverify/multi_log_model.py`に併存させている（一様格子の結果を上書きするのではなく、格子設計のバリエーションとして追加した）。`_model_from_sequences`という共通のモデル構築処理を切り出し、格子の切り方（箱列の作り方）だけが異なる2つの入口として実装している。
