## 1. 目的

Autoware を実走（シミュレーション）させて得られたランタイムログを、既存の **CPD (Car Position Diagram) / GCPD** モデルと突き合わせ、次の2点を検証できるようにする。

1. **適合性検証（membership check）**：観測されたログの挙動が、CPDモデルが表現するシナリオ集合（`gcpd.py` の SAT/SMT 制約が許す `(car, box, lane, position, step)` の割当て空間）に含まれるか。
2. **性質の突合（property cross-check）**：CPDモデル上で成立する性質（衝突可能性など）と、ログから実際に観測される事象（衝突の有無、目標速度への到達など）が一致するか。

これは論文中で今後の課題として挙げられている「CPDモデルを具体的な地図・交通データと統合する」方向性の第一歩であり、CPDを**シナリオ生成**だけでなく**シナリオベース検証**（実行ログの適合性チェック）に使う拡張にあたる。

## 2. 入力データの整理

### 2.1 CPD/GCPDモデル（`gcpd.py`）

`Model` クラスが持つ要素（`sample1.py` より）:

| 要素 | 型 | 意味 |
|---|---|---|
| `cars` | `[str]` | 車両名のリスト（例: `"LCar"`, `"RCar"`） |
| `boxes` | `[(car, box_id)]` | 車両ごとの「箱」＝シナリオの離散状態 |
| `position` | `[(car, box_id, pos:int)]` | 箱の縦方向位置（整数の順序尺度） |
| `lane` | `[(car, box_id, lane:int)]` | 箱が属するレーン番号 |
| `inits` | `[(car, box_id)]` | 各車両の初期箱 |
| `ntrans` / `ctrans` / `netrans` / `cstrans` / `strans` | 遷移 | 通常・条件付き・非存在条件付き・カスタム条件・同期遷移 |
| `max_step` | `int` | シナリオの最大ステップ数 |

`Box(car_index, box_id, step): Bool` が「時刻stepにその箱がアクティブか」を表す一階述語で、`Pos`/`Lane` はその箱の位置・レーンを表す関数。**position と lane は連続座標ではなく、モデル設計者が与える離散的な順序値**である点が、ログとの対応付けで最も注意すべき点になる。

## 3. ギャップ分析

| | CPDモデル | Autowareログ |
|---|---|---|
| 空間 | `lane`（離散整数）・`position`（離散整数、順序尺度） | 連続座標 `x, y, z`（メートル） |
| 時間 | `step`（離散整数、0..max_step） | 連続時刻 `timestamp`（秒、~0.1s刻み） |
| 状態の存在 | 箱＝「その状態が成立している区間」を表す真偽値 `Box(c,n,s)` | 車両は常に存在し続ける連続軌跡 |
| 対象 | 抽象化されたシナリオの等価類 | 1回のシミュレーション実行の具体的トレース |

→ **ログを CPD のボキャブラリ（car, box, lane, position, step）に離散化する変換**が必要。この変換の設計が本ドキュメントの中心課題。

## 4. 提案するマッピング

### 4.1 車両の対応

- Autoware側 `ego` → CPD側 `"Ego"`（既存モデルでの `EgoCar` 系命名に合わせる）
- Autoware側 NPC（本データセットは基本 ego + NPC1台の想定）→ CPD側 `"RCar"` 等、検証対象のCPDモデルで使われている命名に合わせる

### 4.2 空間の離散化

- **lane**: サイドカーの `npc_lateral_m` を用い、egoレーンを `lane=0`、隣接レーンを符号に応じて `lane=1`（右）/`lane=-1`（左）のように量子化する。レーン境界（車線幅）は `jama_road_geometry=non_intersection` 前提のもと、AJISAI側のシミュレーション設定（`metadata`）から車線幅を取得して閾値化する。
- **position**: CPDのpositionは「箱の登場順」を表す順序尺度であり、メートル値そのものではない。したがって、`npc_longitudinal_m` や `delta_lateral_m` の**変化点**（イベント発生前後）を箱の切り替わり点として扱い、position はモデル定義側（検証対象のCPDモデル）にあらかじめ与えられている整数系列にそのまま対応させる。つまり「ログのどの時刻区間がモデルのどの箱に相当するか」を決める問題に帰着させる。

### 4.3 時間（step）の離散化

2方式を候補として提示する。

1. **イベント駆動（第一選択）**：サイドカーの `derivation.reference_frame_timestamp`（ラベル判定時刻）や、速度・横位置の変化が閾値を超えた時刻を「ステップの境界」とする。例えば cut_in なら `[割込み前（走行中）] → [割込み後]` の2ステップに対応し、`max_step=1` のモデルと対応させやすい。
2. **固定間隔（代替案）**：一定Δt（例: 1秒）ごとにサンプリングしてステップ列を作る。より忠実だが `max_step` が大きくなり、SAT制約も比例して増える。まずは方式1でPoCを行い、必要に応じて方式2に拡張する。

## 5. 検証の2モード

### 5.1 適合性検証（Conformance / Membership Check）

離散化して得た `(car, box, lane, position, step)` の割当てを、検証対象の `gcpd.Model` に対する追加制約として solver に投入し（`Box`/`Pos`/`Lane` の値を固定する等式制約を `add`）、モデル本来の制約（`add_pos`, `add_lane`, `add_init`, `add_trans`）と連立させて `solver.check()` を呼ぶ。

- **sat** → ログの挙動はモデルが表現するシナリオ集合の要素として矛盾なく説明できる（適合）。
- **unsat** → モデルが想定していない挙動（モデル外の振る舞い、またはモデルの不備、あるいは離散化の誤り）としてフラグを立てる。

### 5.2 性質の突合（Property Cross-check）

`gcpd.py` の `ps_col`（衝突述語）等を使い、CPDモデル上で「衝突が起こりうる」とされる箱の組と、ログ側で実際に観測される最小車間距離（`groundtruth_kinematic` から計算）やサイドカーの `consistency_ok` を突き合わせる。既にAJISAI側で行われている「filenameベースのラベル」対「trajectoryから導出したラベル」の整合性チェックと同様の考え方を、CPDモデル対ログの整合性チェックに応用する。

### 5.3 ラベルからモデルを自動選択

サイドカーの4軸ラベル（`jama_npc_position` / `jama_npc_direction` / `jama_npc_behavior`）を使い、どの既存CPDモデル（論文中のJAMA用モデル、または `experiment/` 配下のモデル）を検証対象として選ぶかを決めるルックアップテーブルを用意する。

## 6. 実装アーキテクチャ（提案）

`fomaad/sgcpd` 内に新規モジュール `logverify/` を追加する案。

```

├── jama_log.py     # 本体+サイドカーの読み込み → 内部表現 Instance に変換
```

- データセット本体（9.7GB）はリポジトリに含めず、外部パス／環境変数でBoxからの取得先ディレクトリを指定する運用とする。

## 9. 咲川論文に基づく具体化（v0.2）

### 9.1 咲川論文の要点

咲川氏の研究は、本ドキュメントが「4. ギャップ分析」で述べた「CPDの離散な語彙」と「Autowareログの連続な物理量」の間のギャップと**まったく同じ問題**（論文中では「抽象度のギャップ」）を、CPDとは独立に、抽象解釈（データマッピング）の枠組みで扱ったものである。提案されている2手法のうち、特に**車両周辺の領域分割（15領域モデル）**が本プロジェクトとの親和性が高い。

- **9領域モデル**: egoを中心に縦方向3分割（lead / ego / following）× 横方向3分割（left / ego車線 / right）＝9領域（lead-left, lead, lead-right, left, ego, right, follow-left, following, follow-right）。
- **15領域モデル**: 縦方向をさらに5分割（far-lead / lead / ego / follow / far-follow、閾値距離 `Dth = v_ego × 2.0s`）×横方向3分割＝15領域。9領域モデルより高い距離での接近予兆を捉えられ、実験ではFN=0を保ったままTNが改善（誤検知が減少）した。
- **時間の抽象化**：連続する同一の抽象状態を1つに集約するイベント駆動型の圧縮（本ドキュメントv0.1の「4.3 イベント駆動（第一選択）」で提案していたものと同一の考え方）。実データ（AWSIM）で平均状態数10個前後、圧縮率99%超を達成。
- **座標正規化**：ワールド座標系のego・NPC位置を、egoの進行方向を基準とした相対座標系へ回転変換する実装（`normalize_coordinates`）を持つ。これは本ドキュメントの「7. 未決事項 (4) 座標系」に対する具体的な答えを与える。
- **安全性の定義**：相対速度の符号＋領域（前方でPOS＝遠ざかる、後方でNEG＝遠ざかる、なら安全）による安全性判定を提案し、「抽象空間で安全と判定されたら具体空間でも安全」という健全性（over-approximation）を証明している（定理4.1相当）。実験でFN（危険の見逃し）= 0 を達成。
- **既知の限界**（論文7.4節）：(a) 蛇行（swerve）・Uターンのように「向き」の変化が本質的なシナリオは、位置ベースの領域分割だけでは検出できない。(b) 距離と速度を独立に抽象化しているため、安全性判定のFP（過検知）が多い。改善案として「述語抽象化」（例: `TTC<2.0` に相当する述語 `x - 2.0v < 0` を直接抽象状態に持たせる）を提案している。

### 9.2 CPDとの対応づけ（本ドキュメント4節の具体化）

咲川氏の15領域モデルの各シンボルは、**縦方向インデックス×横方向インデックス**の直積として素直に分解でき、これはCPDの `(lane, position)` とほぼそのまま対応する。

| 領域名 | lane（横方向） | position（縦方向、15領域） |
|---|---|---|
| far-left / lead-left / left / follow-left / far-rear-left | +1（左隣接車線） | far-lead=+2 / lead=+1 / ego=0 / follow=-1 / far-rear=-2 |
| far-front / lead / ego / following / far-rear | 0（自車線） | 同上 |
| far-right / lead-right / right / follow-right / far-rear-right | -1（右隣接車線） | 同上 |

（9領域モデルの場合は縦方向を {lead=+1, ego=0, following=-1} の3値に単純化すればよい。）

これにより、**咲川氏の抽象軌道 `T̂rj = ⟨ŝ'_0, ŝ'_1, …, ŝ'_m⟩` は、そのままCPDの箱列に変換できる**：

1. 各抽象状態 `ŝ'_k = (p̂_k, v̂_k)` の領域 `p̂_k` を上表で `(lane_k, position_k)` に変換する。
2. NPC車両について、CPDの箱を `("npc", k)`（`k = 0, …, m`）として生成し、`append_position([("npc", k, position_k)])`、`append_lane([("npc", k, lane_k)])` を登録する。
3. 連続する箱の間に通常遷移を追加する：`add_ntrans(("npc", k, "npc", k+1))`（すべての `k`）。
4. egoは自車中心の相対座標系の原点にあたるため、別途 `("ego", 0)` の固定箱として置くか、モデルの目的に応じて省略する。
5. `set_init([("npc", 0)])`、`max_step = m` として `Model` インスタンスを構成する。

この手順により、**1件のログから、そのログの挙動だけを表す「インスタンスCPDモデル」が機械的に生成できる**。これは咲川氏の「抽象化ツール」の出力形式（`follow-left → lead-left → lead` のような遷移系列）を、そのままCPDのモデル構築APIに流し込むアダプタに相当する。

### 9.3 適合性検証への接続（本ドキュメント5.1節の具体化）

「5.1 適合性検証」で述べた `check_membership` は、次のように具体化される。

1. **参照モデル**：JAMA行動セル（例: cut_in, ahead_right, same_direction）ごとに、許容される箱の遷移パターンを表す「参照CPDモデル」を用意する（`experiment/` にある論文Table Iのレーン変更モデルを参考に、`ntrans`/`ctrans` として「left→ego」「right→ego」等の遷移のみを許可する形で定義）。
2. **インスタンスモデル**：9.2節の手順で、検証したいログ（例: `TD-NI-AR-SD-N04-CI-0010`）から自動生成する。
3. **検証**：インスタンスモデルの `(box, lane, position, step)` 割当てを、参照モデルの制約（`add_pos`, `add_lane`, `add_init`, `add_trans`）に対する追加の等式制約として solver に投入し `check()` する。
   - **sat** → このログの挙動は参照モデルが定義する cut_in シナリオ集合の要素として矛盾なく説明できる。AJISAI側のサイドカーラベル（`jama_npc_behavior="cut_in"`, `consistency_ok=true`）との突合も行い、両者が一致するかを報告する。
   - **unsat** → 参照モデルが想定していない遷移（例：一度自車線に入ってからまた元の車線へ戻る、といった蛇行的な動き）が発生している。これは咲川論文が指摘した「swerve/u_turnを位置ベースの領域分割だけでは検出できない」という限界と表裏一体であり、**CPD側の視点では「参照モデルにない遷移＝新規シナリオ候補（unsat）として自動的に検出される」**という利点に転化できる可能性がある。

### 9.4 安全性判定への接続（本ドキュメント5.2節の具体化）

咲川氏の安全性定義（相対速度の符号＋領域）は、CPDの衝突述語 `ps_col(c1, c2, bx, t)`（同時刻に同じ `lane` かつ同じ `position` にいたら衝突）と両立する。咲川論文が課題として挙げた「距離と速度を独立に抽象化したことによるFP過多」は、まさに論文が提案する「述語抽象化」に相当するものをCPDが最初から備えている、と捉えることができる。すなわち、`Pos` と `Lane` を同時に扱う `ps_col` の条件式自体が、咲川論文で言う「距離と速度（正確には位置と位置）の結合条件」であるため、**CPDに衝突判定を委ねることで、咲川氏の手法単体よりもFPを抑制できる可能性がある**。この仮説はPoCで検証する価値がある。

## 10. cut-in の参照CPDモデルと格子ベース抽象化（v0.3）

### 10.1 動機：なぜ咲川氏の名前付き領域ではなく格子ベースにするのか

第9節までの `cpd_bridge.py` は、咲川氏の15領域抽象化ツールの出力（`lead-right`, `far-front` のような領域名の列）を、`REGION_TO_LANE_POS` という固定のルックアップ表で `(lane, position)` に変換していた。この方式は「1本のログを要約し、そのログ専用のインスタンスCPDを作る」用途には向いているが、次の点で「cut-inというシナリオ集合そのものを表す参照CPD」を**自分たちで直接書き下す**用途には合わない。

- 15領域モデルの境界（`Dth = v_ego × 2.0s` など）は、咲川氏が別の目的（安全性判定）のために選んだ閾値であり、参照CPDを設計する際にこちらが選びたい粒度（例えば「1箱=5m」）とは独立に決まってしまっている。
- 領域名は9〜15種類の固定カテゴリしかなく、参照CPD側で「隣接レーンのどこから出発してもよい」といった**任意の範囲**を表現しようとすると、結局は領域名を経由せずに `(lane, position)` を直接扱いたくなる。

そこで、**参照CPDを設計するときに使う格子のセルサイズ (gx, gy) を先に決め、ログの離散化にも同じ (gx, gy) を使う**、という順番に変更する。ログのどの時刻についても `position = round(rx/gx)`, `lane = round(ry/gy)` という整数がそのまま得られ（`logverify/grid_bridge.py`）、これは参照CPDモデルの `(lane, position)` の語彙と最初から一致する。咲川氏の抽象化との違いは「固定の意味的カテゴリ」対「設計者が選ぶ物差しの目盛り」であり、後者の方が参照CPDの直接記述と相性が良い。

なお、咲川氏の `vendor/trajectory_abstraction/src/abstraction_grid.py` / `safe_grid.py` も内部的に格子ベースの抽象化を実装済みだが、境界が `floor(ry/gy)` で `k=0` が `[0, gy)` と非対称になっている（自車線中心 `ry=0` を跨がない）。`logverify/grid_bridge.py` では `round()` ベースの対称な離散化（`k=0` が `[-gy/2, +gy/2)`）に変更し、「lane=0 は自車線」という直感と一致させている。

### 10.2 cut-in の参照CPDモデル（`logverify/reference_models.py`）

`build_cutin_reference(i_range, side_lanes=(-1,1), ego_lane=0)` が、次の形の `gcpd.Model` を機械的に生成する。

1. **状態空間**：`side_lanes ∪ {ego_lane}` の各レーンと、`i_range` の各縦方向位置の直積を、それぞれ1つの箱として列挙する（`i_range` を広く取るほど、扱える縦方向レンジが広がる）。
2. **隣接レーン内の移動**：レーンを跨がずに `position` が ±1 だけ変わる遷移（接近・離反）。
3. **合流（cut-inの核心）**：隣接レーンから `ego_lane` へ、`position` が高々1変化して移る遷移。
4. **合流後**：`ego_lane` 内でのみ `position` が変化できる。**隣接レーンへ戻る遷移は一切定義しない。**
5. **非決定的な出発点**：実座標を持たないダミーの開始箱（`START_BOX`）を1つ用意し、そこから隣接レーンの任意の箱へ遷移できるようにする。こうすることで「隣接レーンのどこから出発してもよい」「左右どちらの隣接レーンから来てもよい」という非決定性を、`gcpd.Model` が前提とする「各車について常にちょうど1つの箱がアクティブ」という不変条件を壊さずに表現できる（詳細はモジュール内のコメントを参照）。

4番目の制約が「カットイン」と「蛇行(swerve)」を区別する核である。一度合流したあとに元のレーンへ戻る、あるいは往復するようなトラジェクトリは、対応する遷移が存在しないため、この参照モデルでは構造的に受理されない。

### 10.3 適合性検証（`logverify/membership.py`）

`check_membership_cutin(model, observed)` は、観測された `(lane, position)` の列（`logverify/grid_bridge.py` が出力する圧縮済みグリッド状態列からそのまま作れる）を、参照モデル自身の制約（`add_pos`, `add_lane`, `add_init`, `add_trans`）に対する追加の等式制約として solver に投入し、`solver.check()` を呼ぶ（5.1節・9.3節で述べた方式の実装）。

- **観測の各ステップ** t について「その `(lane, position)` を持つ箱のどれかがアクティブ」という論理和制約を追加する（該当する箱が1つも無ければ、その時点で構造的にUNSATと確定する）。
- ダミー開始箱の分、観測列の先頭はモデルの step 1 に対応する（`start_offset=1`）。
- `gcpd.py` はモジュールレベルの可変な `solver`/`c2i` を持つため、`check_membership` は呼び出しのたびに明示的にリセットする（`reset_solver()`）。

`logverify/demo_cutin_membership.py` で、実データが手元になくても検証できる3種類の合成トラジェクトリ（典型的なcut-in／最初からego車線／合流後に元のレーンへ戻る蛇行）に対してこのパイプラインを流し、期待通り SAT / UNSAT / UNSAT が得られることを確認済みである。

```
$ python3 -m logverify.demo_cutin_membership
cutin_like        : SAT
stays_in_own_lane : UNSAT
swerve_like       : UNSAT
```

### 10.4 未検証・今後の課題

1. **実データでの検証**：本節のパイプラインは合成トラジェクトリでのみ検証済みであり、AJISAIの実ログ（cut_in 94件）に対してはまだ流していない。`logverify/grid_bridge.py` の `grid_states_from_json(path, gx, gy)` はAJISAIの `<id>.json`（`groundtruth_kinematic`）にそのまま使える設計だが、外部（Box）からデータセットを取得できる環境で実行する必要がある。
2. **セルサイズ (gx, gy) の選び方**：本節のデモでは `gx=5.0m, gy=3.5m`（車線幅相当）を暫定的に使ったが、これがAJISAIの実データに対して適切か（粗すぎて別々の状態を同一視してしまわないか、細かすぎて `i_range` が発散しないか）はPoCで確認する必要がある。咲川論文・`safe_grid.py` が実験しているセルサイズの候補（`(1.0,1.0), (1.75,1.75), (3.5,3.5)` 等）を横展開して比較するとよい。
3. **cut_out・deceleration との切り分け**：本節の参照モデルは「隣接レーン→egoレーン」の合流のみを許すため、cut_out（逆方向）や lane change を伴わない加減速シナリオは自動的にUNSATになる（＝別の参照モデルが必要、という結果自体は意図通り）。cut_out用の参照モデル（`ego_lane`→隣接レーンの合流のみ許す、対称な定義）を同様に用意し、`jama_npc_behavior` ラベルとの一致率を集計するのが次の一歩になる。
4. **咲川氏の安全性判定との統合**：9.4節で述べた `ps_col`（CPDの衝突述語）による突き合わせは、本節の格子ベースの参照モデルに対してもそのまま適用できるはずであり、まだ試していない。
5. **蛇行(swerve)の扱いの一般化**：本節のUNSAT判定は「一度合流したら戻れない」という単一の制約に基づく。実際のswerveはもっと多様なパターン（合流せずに近づいたり離れたりを繰り返す等）を含みうるため、`side_lanes` 内の往復も含めて「何が蛇行としてUNSATになるべきか」をAJISAIのswerveラベル（130件）で確認し、必要なら参照モデルをさらに洗練する。

### 10.5 距離帯・並走・加速のバリエーションを1つのモデルに統合する（v0.4）

10.2節の初版は `i_range` を生の格子インデックス（例えば0〜19の20値）でそのまま箱にしていたため、近距離・中距離・遠距離それぞれで始まるcut-in、あるいは隣接レーンでしばらく並走してから加速して合流するcut-inを扱おうとすると、`i_range` を広げる必要があった。しかし箱の数は `|lanes| × |i_range|` で増え、遷移（隣接レーン内・合流・ego車線内）を総当たりで張ると箱数の2乗のオーダーで増えるため、`i_range` を広げるとソルバが実用的な時間で終わらなくなることが分かった（20値程度で2分のタイムアウトに達した）。

これは「CPDのpositionは連続座標ではなく順序尺度である」という2.1節の指摘を、参照CPDの設計そのものにも適用すべきだったということである。そこで `logverify/zones.py` を追加し、縦方向の距離 `rx` を「後方(-1) / 近距離(0) / 中距離(1) / 遠距離(2)」という4値の順序尺度に丸めてから箱を作るようにした（`reference_models.build_cutin_reference` のデフォルトの `i_range` もこの4値になった）。これにより：

- 箱の数は距離レンジによらず一定（`|lanes| × 4`）になり、ソルバは瞬時に終わる。
- 「近距離cut-in」「中距離cut-in」「遠距離cut-in」「隣接レーンで並走してから加速して合流するcut-in」は、いずれも**同じ1つの参照CPD**（`build_cutin_reference()` の1回の呼び出し）に対する、それぞれ異なるSATの充足解（witness）として表現される。これがCPDの強み（「バリエーションを1つのモデルで書ける」）を実際に確認できた点である。
- `logverify/report.py` の `summarize_trace` / `describe_scenario` が、SATと判定されたログの `(lane, position=zone)` の系列を、実際にどの距離帯から出発し、どこで並走したとみられ、どこで合流したかという日本語の要約に変換する（並走の判定は、圧縮済み状態の継続フレーム数がしきい値以上かどうかで行う。position自体は既に距離帯に丸められているため、「同じ距離帯の状態が何個続くか」ではなく「1状態がどれだけ長く継続したか」で判定する必要がある点に注意）。

`logverify/demo_cutin_membership.py` で、近距離・中距離・遠距離・並走+加速の4種類のcut-inと、2種類の負例（ego車線に留まり続ける／蛇行）を同じ参照モデルに対して判定し、期待通りの結果（前者4つはSAT、後者2つはUNSAT）を得ている。

今後の課題として、10.4節の内容に加えて次を追加する。

6. **距離帯のしきい値 (`ZoneThresholds`) の妥当性**：本節では `near_max=5m, medium_max=20m` を暫定的に使ったが、AJISAIの実データにおける典型的なcut-in開始距離の分布を見て調整する必要がある。
7. **「並走」判定のしきい値**：`parallel_min_frames`（継続フレーム数）は暫定値であり、実データのサンプリング間隔（約0.1秒）を踏まえて、何秒以上の並走を「並走」とみなすかを再検討する。

## 11. ログからCPDを構築する3つの方法（v0.4）

ここまでで、ログからCPDを構築・利用する方法が複数出てきた。それぞれ目的が異なるため、どれか1つに統合するのではなく、**3つの独立した方法として`logverify/`（および`vendor/`）に併存させる**方針とする。

**咲川氏のvendorコードへの依存について**: 方法B・方法C（`logverify/`配下）は、咲川氏の`vendor/trajectory_abstraction/`配下のコードには一切依存せず、独立に実装している。咲川氏のコードを使うのは方法A（`vendor/trajectory_abstraction/src/cpd_bridge.py`）のみである。なお、実装の初期段階で`logverify/grid_bridge.py`に咲川氏の座標正規化関数（`normalize_coordinates`等）を再利用する`grid_states_from_json`関数を用意していたが、実際にはどの方法でも使われておらず（合成トラジェクトリでのテストに留まっていたため）、方法B・Cをvendorコードから完全に独立させる方針のもと削除した。実データ（AJISAIログJSON）からego基準の相対座標を取り出す部分が必要になった際は、`logverify/`内で独立に実装する。

| | 方法A（既存） | 方法B | 方法C |
|---|---|---|---|
| 実装 | `vendor/trajectory_abstraction/src/cpd_bridge.py`（第9節） | `logverify/reference_models.py` + `logverify/zones.py`（第10節） | `logverify/multi_log_model.py`（本節） |
| 入力 | ログ1本 | 「シナリオ集合」の定義（設計者が手で書く） + 検証したいログ | ログN本（複数） |
| 出力 | そのログ専用の「インスタンスCPD」 | 参照CPD（cut-inなど）と、ログがそれに適合するか(SAT/UNSAT) | N本のログをまとめて表す「統合CPD」 |
| 抽象化の単位 | 咲川氏の名前付き領域（9/15領域） | 距離帯（近距離/中距離/遠距離、順序尺度） | 生の格子（ログを区別できる最小の細かさまで自動的に細かくする） |
| 主な用途 | 1本のログを要約・可視化する | 「これはcut-inか？」を判定し、どの距離帯・並走の有無かを分類する | 複数の実例から、それらを包含するシナリオ集合を機械的に構築する |

### 11.1 方法C：複数ログの統合CPD構築

ご相談の「複数のログがあったときに、それを1つのCPDとしてモデル化する」方法である。方針は次の通り。

1. **格子の自動選定**：`multi_log_model.find_distinguishing_grid` が、粗い格子（デフォルト `gx=5.0m, gy=3.5m`）から始めて、**全てのログが互いに異なる箱列に離散化されるまで**格子を半分ずつ細かくしていく。2本のログが物理的には別々の挙動でも、粗い格子では同じ箱列に潰れてしまうことがあるため（実際、`gx=5.0, gy=3.5` で区別できなかった例を確認済み）、常に「今与えられたログ集合を区別するのに十分なだけ」の細かさを自動的に選ぶ。
2. **統合モデルの構築**：`multi_log_model.build_union_model` が、各ログの箱列（(lane, position)の系列）を、1つの`gcpd.Model`の中の「そのログが辿った経路」として書き込む。複数のログが同じ箱を通れば、そこでモデルの中の経路が自然に合流する。実座標を持たないダミーの開始箱（`START_BOX`）を使い、「どのログの出発点から始まってもよい」という非決定性を、方法Bと同じ仕組みで表現する（10.2節参照）。
3. **含意の確認**：`multi_log_model.verify_logs_included` が、統合モデルに対して各ログの箱列がmembership check（第10.3節と同じ仕組み）でSATになることを確認する。
4. **シナリオ列挙による検証**：`multi_log_model.count_scenarios` / `enumerate_scenarios` が `gcpd.s_count` / `gcpd.enum_ss`（3節・9.6節でも使っている、CPDの標準的なシナリオ列挙機能）をそのまま呼び出し、統合モデルから実際に列挙されるシナリオの総数と中身を返す。**列挙されたシナリオ数が入力したログの本数と一致すれば「一般化なしでログがそのまま再現された」ことを、それより多ければ「複数のログの部分列が組み合わさり、入力にはなかった新しい経路も生成された」ことを意味する**。後者はまさにCPDが持つ「具体例の集合から、それらを包含する一般化されたシナリオ集合を作る」という能力の現れである。

`logverify/demo_multi_log_model.py` で、4本の合成ログ（右隣接レーン近距離/遠距離からのcut-in、左隣接レーンからのcut-in、自車線に留まり続けるログ）を統合し、期待通り4本すべてがSATで含まれ、シナリオ列挙数も4（＝この例では偶然どのログも他のログと箱を共有しなかったため一般化は起きなかった）であることを確認した。また、2本のログが粗い格子では同一の箱列に潰れてしまう例を作り、格子の自動細分化によって正しく区別されることも確認した。

### 11.2 未検証・今後の課題（方法C）

1. **実データ10本での検証**：ご相談にあった「10個のログを区別できる格子で1つのCPDにする」を、実際のAJISAI cut_inログ10本程度で試す。ログ本数が増えると、格子をどこまで細かくすれば全てを区別できるかが非自明になる可能性がある（`find_distinguishing_grid`の`max_iters`で頭打ちになるケースを実データで確認する）。**11.8節で、実際のAJISAIログ1本を使った検証を行った（実データでの検証の第一歩）。ただし1本のみであり、10本規模での検証はまだ残っている。**
2. **意図した一般化と意図しない一般化の区別**：統合モデルが入力より多くのシナリオを生成した場合、それが「望ましい一般化」（例：cut-inのタイミングだけが違う2本のログが、共通の合流点を経由することで自然に組み合わさる）なのか、「格子が粗すぎたことによる意図しない混線」なのかを区別する基準が必要。方法Bの距離帯（順序尺度）の考え方を方法Cにも取り入れ、「区別すべきものは区別し、区別しなくてよいものは積極的にまとめる」バランスを取ることが次の課題になる。**11.7節で、Egoに近い部分は細かく・遠い部分はまとめる非一様格子（`build_union_model_near_far_grid`）という第一歩を実装した。ただしこれは「Egoからの距離だけ」に基づく単純な切り方であり、「望ましい一般化かどうか」を判定する基準そのものはまだない。**
3. **方法A・Bとの接続**：方法Cで作った統合CPDに対して、方法Bの参照CPD（cut-inの一般形）との関係を調べる（統合CPDのシナリオが、方法Bの参照CPDのmembership checkをすべて通るか、など）。

### 11.5 Egoが前進するワールド座標系でのアニメーション

#### v1（初版、可視化側だけの後付け）

11.3節のGIFは、モデルが持つ`(lane, position)`をそのまま「ego基準の相対座標」の格子とみなし、egoを`lane=0, position=0`に静止させて描いていた。しかし実際にはegoも道路上を前進しており、positionが変化しないのは「NPCとの相対距離」を状態として使っているからに過ぎない。論文的な見た目にする際、egoも動いているように見せたいという要望を受け、`logverify/world_frame_gif.py`の初版では、Egoが一定速度で前進すると仮定し（`ego_world_position(step) = step × ego_speed`）、NPCの絶対位置を`ego_world_position(step) + モデルが持つ相対position`として可視化側だけで計算していた。

これに対し「オリジナルの英語の論文では、CPDでEgoが動いているようにモデル化しているはず」という指摘を受けた。論文（Fig.2/Fig.7）を確認すると、確かにEgoも他の車（LCar, RCarなど）と同じく1つの car として、"positionは箱の並び順そのもの"という規約（concrete box、論文IV-C節）に基づく箱列を持つ形でモデル化されている。v1はCPDモデル自体にはEgoという car が存在せず、可視化側だけの後付け計算に留まっていたため、この指摘は正しい。

#### v2（Egoを実際にCPDの car として追加）

`logverify/ego_car.py`の`with_ego_track`を追加し、Egoを実際にCPDの car として追加したモデルを構築するようにした（`logverify/world_frame_gif.py`はv2としてこれを使うよう全面的に書き直した）。

素朴には「Ego(0)->Ego(1)->...->Ego(max_step)という独立した箱列をNPCと同じモデルに追加するだけ」で良さそうに思えるが、これはうまくいかない。gcpd.py の`add_trans`は、1ステップにつき「登録されている遷移のうちどれか1つだけが発火する（＝1台の車だけが箱を変える）か、何も起きないか」という排他的選択を各ステップに課している（sample2.pyのLCar/RCarのように、2台が独立に「互いに異なるステップで」進むことは表現できるが、「2台が同じステップで同時に進む」ことは表現できない）。そのため、Egoに独立した箱列を追加しただけだと、EgoとNPCは同じステップ予算を奪い合う「独立に進む2台の車」になってしまい、Egoが毎回確実に前進する保証がなくなる（NPCの遷移が選ばれた回数のぶんだけEgoは足止めされる）。

そこで、論文の定義3で正式に定義されている**同期遷移（Es、gcpd.pyでは`strans`）**を使った。これはFig.8のblind spot事例で「青い車が車線変更すると同時に赤い車も動く」という記述に対応する、CPD本来の機構である。NPC側の全ての通常遷移（各距離帯・車線間の遷移）それぞれに対して、「そのNPCの遷移が発火するときは、Egoの箱列も同時に1つ進む」という同期遷移グループを機械的に生成し、NPC側の元の通常遷移は（単独では発火できないよう）この同期版に置き換える。これにより、

- NPCが実際に距離帯・車線を変える瞬間には、必ずEgoも1つ前進する。
- NPCが変化しないステップでは、Egoも変化しない（「何も起きないステップ」として扱われる）。
- Egoの経路は常に一本道（Ego(0)->Ego(1)->...）なので、これによってNPC側の充足解の集合が変わることはない（`logverify/demo_world_frame_gif.py`で方法Cの4本の合成ログについて確認したところ、Egoを追加する前後でシナリオ数が4のまま変わらないことを確認した）。

というEgoの前進が、CPDが表現するシナリオの一部として（可視化のための後付けではなく）solverが解いた結果そのものとして得られるようになった。

NPC側の position は（方法B・Cとも）Egoとの相対距離をそのまま表しているため、1枚の固定カメラの絵として描画する際には、`NPCの絶対position = Ego(box).position（=これまでの同期前進の回数） + NPCの相対position`として画面上の座標に変換する（この変換自体は見た目のためのもので、CPDが表現するシナリオ集合の意味＝相対距離ベースを変えるものではない）。lane（横方向）はもともとego基準の相対値（隣接レーン=-1/1など）なので変換不要で、そのまま「egoからの左右オフセット」として使う。カメラはワールド座標系に固定（egoを追従しない）。

- 方法Bの参照CPDは非決定性が大きく全列挙が膨大になりうるため、可視化用には`num_model`で列挙数を絞れるようにした（`logverify/demo_world_frame_gif.py`では代表6シナリオに絞っている）。方法Cの統合モデルはログ本数が確定しているため通常はそのまま全列挙してよい。
- `ego_speed`（Egoの箱番号を画面上の格子セル数に変換するスケール）の意味合いは、相対distanceが順序尺度（距離帯）である方法Bと、実際の格子（メートル単位）である方法Cとで厳密には異なる点には注意が必要。Egoの絶対速度自体はログの相対座標だけからは復元できない情報であり、あくまで見た目のためのパラメータである。
- 本節の同期は`model.ntrans`（通常遷移）のみを対象としている。現状の方法B・Cのモデルはntransしか使っていないため問題にならないが、将来`ctrans`/`netrans`等を使うモデルにEgoを追加する場合は`ego_car.py`の拡張が必要になる。

今後の課題として、`ego_speed`を実データ（AJISAIログの座標変換前の絶対座標、あれば）から推定し、より物理的に正確なアニメーションにすることが挙げられる。

#### 描画上の注意: 距離帯（順序尺度）をそのまま座標に足すと衝突に見える

v2のアニメーションを実際に見たところ、cut-in参照CPD（方法B）でNPCがEgoと完全に重なって「衝突しているように見える」場面があった。原因は、方法Bのpositionが`logverify/zones.py`の BEHIND=-1 / NEAR=0 / MEDIUM=1 / FAR=2 という**順序尺度の距離帯カテゴリ**であり、実際のメートル距離ではないことにある。「NPCの絶対position = Egoの絶対position + NPCの相対position」という変換式にNEAR=0をそのまま代入すると、数値としてはEgoの座標にちょうど0を足すことになり、Egoとまったく同じ格子セルに描画されてしまう。これはモデルが「衝突するシナリオ」を表しているわけではなく、「近い」という抽象的な分類がたまたま0という数値で表現されていたことによる、レンダリング上のアーティファクトである（衝突可能性の判定自体は9.4節の`ps_col`と組み合わせる別の話であり、本節の参照CPDにはまだ組み込んでいない）。

対策として、`render_world_frame_gif`に`zone_ahead_offset`引数を追加した。0以上（Ego手前ではない側＝NEAR/MEDIUM/FAR）の距離帯にだけ一律のオフセットを足すことで、NEARがEgoとちょうど同じセルに重ならないようにする（BEHINDは既に負の値でEgoより手前と区別がついているため対象外）。方法Bを描画する際は`zone_ahead_offset=1`以上を指定する。方法C（positionが実際の格子＝メートル単位）では、0が本当に「ほぼ同じ位置」を意味しうるため、デフォルトの0（オフセットなし）のままにしておく。

#### 描画上の注意（続き）: 車線変更の直線補間・車の描画サイズ

上記の修正後も、「NPCが上からEgoに重なって下に移動しているように見える＝衝突しているのでは」という指摘を受けた。実際にGIFのピクセルを追跡して確認したところ、レーン変更を伴う遷移で本当に矩形が重なっているフレームが複数あった。原因は2つあった。

1. **車線変更の直線補間**: (旧レーン, 旧position)から(新レーン, 新position)へ愚直に直線で補間すると、横方向(レーン)と縦方向(position)が同時に動くため、斜めに突っ切る軌跡がEgoの位置をかすめることがある。参照CPDの`max_position_jump`を1に制限しても（距離帯を1段ずつしか変えられないようにしても）、レーン変更自体は起きるため、この現象は解消しなかった。根本的な対策として、レーン変更を伴う遷移では「まず現在のレーンのままposition だけ動き、その後にレーンだけを切り替える」という2段階の中間フレームを挿入するよう`render_world_frame_gif`を変更した（実際の車線変更＝縦に詰めてから横に合流する、という一般的な運転動作にも近い）。これはCPDが検証した状態そのものは変えず、描画上の補間経路を分割するだけである。
2. **車の描画サイズがセル幅を超えていた**: `gcpd_gif.VehicleGif`のデフォルトの車の矩形幅（100px）が、本アニメーションで使っていた1セルの幅（`grid_scale=120px`）に対してmarginと合わせると収まりきらず、**隣接するレーンの車同士が、実際にはレーンが違うのに矩形が視覚的に重なって**しまっていた。車の幅・高さをセル幅に収まるよう縮小し、marginもそれに合わせて調整した。

修正の効果をピクセル単位で検証したところ（`world_cutin.gif`で赤と青の矩形のbounding boxが実際に重なっているフレーム数をカウント）、修正前は15回の重なりがあったのに対し、修正後は0回になった。なお、NPCがEgoと同じレーン・同じ距離帯（NEAR）まで実際に近づく場面自体は今後も起こりうる（それ自体はモデルが表現している通りの状態であり、隠すべきものではない）。今回直したのは、モデルが表現していないはずの中間軌跡や、レーンが違うのに重なって見えるという、純粋な描画上の誤りである。

#### モデル構造図へのEgoの反映

11.4節の`plot_model_paper_style`はNPC側のスイムレーンしか描かないため、Egoが実際にCPDの car として存在することを図でも確認できるよう、`logverify/model_diagram.py`に`plot_model_with_ego_paper_style`を追加した。NPC側のスイムレーンの上に、Egoの箱列（Ego(0)->Ego(1)->...）を緑色の帯で追加している。同期遷移（strans）は「NPCのntrans1本ごとにEgoの箱番号すべてとの組」を機械的に生成しており、実際の組み合わせ数は膨大（`|ntrans| × ego_max_step`）になるため、1本ずつ線で結ぶと図が読めなくなる。そのため、同期の事実は図中の注記テキストで示すに留めている。`logverify/demo_model_diagram_with_ego.py`で方法B・方法Cの両方について生成・確認した。

### 11.6 方法Cの大規模化（合成ログ19本）

11.1節の確認は合成ログ4本のみで行っており、しかも4本はどれも縦方向（rx）の範囲が互いに重ならないように選んであったため、格子の自動細分化がほとんど試されていなかった。「今は4本しか使っていないが、もう少し大きい規模の実験ができるか」という要望を受け、`logverify/demo_multi_log_model_large.py`を追加し、方法Cのみを対象に規模を広げた実験を行った。

**入力ログの構成（合成、19本）**：右隣接レーンからのcut-in（近距離/中距離/遠距離×各2本）、左隣接レーンからのcut-in（近距離2本＋中距離・遠距離各1本）、自車線に留まり続けるログ（3本、あえて他のcut-inログとrxの範囲を重複させている）、隣接レーンで並走してから合流するログ（左右各1本）、一度合流してから再び隣接レーンへ抜けるcut-in+cut-outログ（左右各1本）、蛇行(swerve)のようなログ（2本）、の8カテゴリを組み合わせた。4本のときと異なり、rxの範囲を意図的に重複させたログを複数含めている点が格子選定への負荷を高めている。

**結果**：

- 格子の自動選定はデフォルトの`gx=5.0, gy=3.5`のまま（細分化の反復なし）で19本すべてを区別でき、格子選定＋統合モデル構築は数秒未満で完了した。19本程度・このような合成ログの多様性であれば、デフォルトの粗い格子でも十分に区別できることが分かった。
- 統合モデルの箱数は33（ダミー開始箱を含む）、`max_step=6`。
- membership check（19本全てが統合モデルに含まれるかの確認）は31.03秒で完了し、19本全てSATであることを確認した。
- シナリオ列挙数は29（入力19本より10多い）。4本のときはシナリオ数が入力本数と一致し一般化が起きなかったが、rxの範囲を意図的に重複させたことで、複数ログが箱列の一部を共有し、入力にはなかった経路が10本追加で生成された。これは11.2節の課題2「意図した一般化と意図しない一般化の区別」に直接関わる観察であり、格子・ログの与え方次第で一般化の起き方が変わることが具体的に確認できた（どの追加経路が「望ましい一般化」でどれが「意図しない混線」かの評価は今後の課題のまま）。
- モデル構造図（`plot_model_with_ego_paper_style`、11.5節）はこの規模でも問題なく描画できた（`model_multilog_large_with_ego.png`）。
- 一方、Egoを同期遷移（strans）で実際にCPDのcarとして追加したワールド座標系アニメーション（11.5節のv2、`with_ego_track`ベース）は、この規模（33箱、`max_step=6`）では同期遷移グループの組み合わせ数（NPCの通常遷移数×Egoの`max_step`）が膨れ上がり、480秒経っても計算が終わらなかった。そのため大規模デモでは、Egoを同期させない単純な静止Ego版（11.3節の`gif_viz.py`、`render_scenarios_gif`）にフォールバックしたところ97.19秒で描画できた（`multilog_large.gif`）。この点は11.7節で解消した（詳細はそちらを参照）。

以上より、方法Cのモデル構築・membership check・シナリオ列挙といった検証の中核部分は19本規模でも実用的な時間で動作することを確認できた。ただし本節の実験はいずれも合成データであり、実データ（AJISAIログ）による検証は11.2節の課題1として引き続き残っている。

### 11.7 大規模モデルでのアニメーション高速化：全列挙をやめる／格子を非一様にする

11.6節でEgoを同期させたワールド座標系アニメーションが19本規模でタイムアウトした件について、2つの指摘を受け、それぞれ対策を実装・検証した。

**(1) そもそも全シナリオを列挙する必要はない**。`check_membership`（本節冒頭、membership.py）を見直すと、「ログが統合CPDに含まれるか」の検証は、統合CPD自身の制約とログの箱列の制約を1つのsolverに投入し、`solver.check()`を**1回だけ**呼んでSAT/UNSATを見ているだけで、`gcpd.enum_ss`のような解の列挙は元々使っていない。19本のmembership check（31秒）もEgoなしでこの方式のまま高速に動いている。一方、アニメーションで`enum_ss`を使っていたのは「絵として見せるための具体的なシナリオを何本か取り出す」ためであり、検証のためではない。そこで`render_world_frame_gif`の`num_model`（列挙するシナリオ数の上限）を、可視化に必要な数個（実験では5）に絞ったところ、19本規模のモデルでも約19〜30秒で描画が完了することを確認した（`num_model=3`で22.6秒、`5`で30.3秒、`8`で41.6秒、と列挙数にほぼ比例して増加する一方、`num_model`を小さく保つ限り実用的な時間に収まる）。

**(2) 格子の設計を、Egoに近い部分は細かく・遠い部分はまとめる非一様なものに変える**。11.1節の格子は、Egoからの距離(rx)・レーン(ry)いずれについても一様なセルサイズを使っていた。しかし「Egoに近い部分の挙動は詳しく区別する必要があるが、遠い部分は多少まとめてしまってよい」という考え方（まさに方法Bの距離帯＝順序尺度の発想であり、11.2節の課題2「方法Bの距離帯の考え方を方法Cにも取り入れる」の第一歩にあたる）に基づき、`grid_bridge.grid_index_variable`と`multi_log_model.build_union_model_near_far_grid`を追加した。`|rx| <= rx_near_range`の範囲は従来通りのセルサイズ（実験では5m）で細かく量子化し、それを超える範囲はより粗いセルサイズ（実験では10m）でまとめる。19本のログに対して`rx_near_range=45m`（後述の理由でこの値を選んだ）、遠方セル10mで試したところ、

- 箱数：33 → 28
- max_step：6 → 5
- membership check：19/19 SAT（31.83秒 → 20.58秒）
- シナリオ列挙数：29（一様格子と同じ、生成された一般化の本数は変わらなかった）

と、モデルのサイズを縮小しつつ、検証結果自体（含意関係・一般化の起き方）は変わらないことを確認した。`rx_near_range`は機械的に決めたものではなく、今回の合成ログの「中距離」カテゴリ（rx=20付近から始まる）が遠方セルとの境界をまたいで区別できなくなる（`cutin_right_medium_1`と`_2`などが同じ箱列に潰れる）ことを実際に確認しながら、それを避けられる値（45m）まで広げて選んだ。

この経緯自体が「近い/遠いの境界と遠方セルサイズは、ログを区別できるように設定しなければならない」という当然の懸念を裏付けている。そこで、`build_union_model_near_far_grid`にも`build_union_model`と同じ安全装置を追加した。具体的には`find_distinguishing_near_far_grid`（`find_distinguishing_grid`の非一様格子版）を追加し、`rx_near_range`・`rx_near_cell`は呼び出し側の指定のまま固定し、`rx_far_cell`だけを（デフォルトで、または`auto_grid=True`のとき）自動的に調整する。`build_union_model_near_far_grid`は、`auto_grid=False`で明示的な値を指定した場合も含め、最終的に得られた格子で全ログが区別できているかを関数内部で必ず検証し、区別できていなければ（一様格子版の`build_union_model`と同様に）`ValueError`を送出する。つまり「区別できない非一様格子が黙って使われてしまう」ことは起きない。

「遠方のセルの統合はできるなら行えばよい（必須ではない）」という方針を受け、`find_distinguishing_near_far_grid`は次の2段階で探索する。

1. 指定した初期値`rx_far_cell0`で区別できない場合：従来通り、区別できるまで半分ずつ細かくしていく（`rx_far_cell`が`rx_near_cell`まで縮まれば、実質的に一様格子と同じ区別能力に収束するため、その一様格子で区別できるログ集合であれば必ず有限回で見つかる）。
2. `rx_far_cell0`ですでに区別できる場合：まだ粗くする余地があるかもしれないので、2倍ずつ大きくしながら「区別できなくなる境界」を探し、見つかったら区別できる側と区別できない側の間を二分探索して、区別できる最大の`rx_far_cell`（＝最大限まとめた粗さ）に絞り込む。

実際に`rx_near_range=25m, rx_far_cell0=10m`（区別できない組み合わせ）を`auto_grid=False`で指定すると`ValueError`になり、`auto_grid=True`（デフォルト）で同じ値から始めると自動的に区別できる格子（この場合は`rx_far_cell`が`rx_near_cell`の5mまで縮まり、一様格子と同じ33箱に収束）を見つけて成功することを確認済み（段階1の動作）。19本のログに対して`rx_near_range=45m, rx_far_cell0=10m`から出発すると、10mですでに区別できるため段階2の「粗くする方向」の探索が働き、最終的に`rx_far_cell=33.75m`まで粗くしても19本全てを区別できることが分かった。これにより

- 箱数：33（一様格子）→ 28（`rx_far_cell=10m`固定）→ 27（`rx_far_cell=33.75m`まで最大限まとめた場合）
- max_step：6 → 5 → 5
- membership check：19/19 SAT（31.83秒 → 19.57秒）
- シナリオ列挙数：29（一様格子と同じ、生成された一般化の本数は変わらなかった）

と、遠方をさらに粗くしても検証結果自体は変わらないことを確認した。なお、`rx_near_range`自体（近い/遠いの境界をどこに置くか）は今回のところ手動で決めており、これを自動で探索する仕組みはまだない（`rx_far_cell`側だけの探索では、境界の置き方自体が悪い場合、`rx_near_cell`まで縮んで一様格子に戻るだけでモデル縮小の効果が得られないことがある。近い/遠いの境界も含めて「区別を保ったまま最大限まとめる」自動探索は今後の課題）。

**(1)(2)を組み合わせた結果**：非一様格子のモデル（27箱、max_step=5、`rx_far_cell=33.75m`まで自動的に最大限まとめたもの）に対して`num_model=5`でEgoを同期させたワールド座標系アニメーションを生成したところ、17.58秒で完了した（`multilog_large_with_ego.gif`、対応するモデル構造図は`model_multilog_large_near_far_with_ego.png`）。11.6節で480秒経っても終わらなかったのと同じ規模のログ集合に対して、Egoを実際にCPDのcarとして同期させた「論文と同じモデル化」でのアニメーションが実用的な時間で得られるようになった。

なお、`build_union_model`（一様格子）と`build_union_model_near_far_grid`（非一様格子）は、どちらも方法Cの実装として`logverify/multi_log_model.py`に併存させている（一様格子の結果を上書きするのではなく、格子設計のバリエーションとして追加した）。`_model_from_sequences`という共通のモデル構築処理を切り出し、格子の切り方（箱列の作り方）だけが異なる2つの入口として実装している。

### 11.8 実際のAJISAIログ1本での検証（初めての実データ）

これまでの実験（11.1〜11.7節）は全て、手で書いた合成トラジェクトリを使ったものだった。本節では、初めて実際のAJISAIログ（JAMA-Traceable ADS Runtime Log Dataset、`TD-NI-AR-SD-N04-CI-0035.json`、NPC1台によるcut-inシナリオ、Autowareシミュレーションで記録）を使い、方法B・方法Cのパイプライン全体を通してみた。

**実データからの(rx, ry)抽出**：AJISAIのログ形式は`groundtruth_kinematic`という配列に、各タイムスタンプでのego・NPCの世界座標系での位置(x, y, z)と姿勢(`rotation.z`、度)が同期して記録されている。`logverify/grid_bridge.py`に`relative_xy_from_ajisai_groundtruth`を追加し、次の手順でego基準の相対座標`(rx, ry)`を計算する。

1. egoの`rotation.z`から、世界座標系でのegoの前方単位ベクトル・左方単位ベクトルを求める。`rotation.z`が標準的な数学の角度（+x軸から反時計回りに測った角度、度）として使えることは、連続する2フレームのego位置の変位ベクトルの向きと`rotation.z`が一致することを実データで確認した上で採用した。
2. NPCとegoの位置の差分（世界座標系）を、上記の前方・左方ベクトルに射影し、`rx`（前方距離）・`ry`（左方向のオフセット、logverify全体のry符号の規約＝正が左隣接レーン側、負が右隣接レーン側、と一致）を得る。

このログでは1697フレーム分の`(rx, ry)`が得られ、`rx`は12.59m〜117.00m、`ry`は-3.04m〜0.54mの範囲だった（右隣接レーン、遠距離から始まりego車線へ合流する、という典型的なcut-inの形）。

**方法B（membership check）**：`logverify.zones.zone_states_from_relative_xy`で距離帯（BEHIND/NEAR/MEDIUM/FAR）に丸め、イベント駆動で圧縮すると、4つの状態`[(-1,2)@632フレーム, (0,2)@4フレーム, (0,1)@272フレーム, (0,2)@789フレーム]`に圧縮された（右隣接レーン・遠距離で長く並走 → 遠距離のままego車線へ合流 → 中距離まで接近 → 再び遠距離まで離れる）。これを10.1節のcut-in参照CPDに対して`check_membership_cutin`で判定したところ、**SAT**（適合する）を確認した。`report.summarize_trace`/`describe_scenario`による自動要約も「出発: 右隣接レーン、遠距離」「合流: ステップ1、遠距離でego車線へ合流」と、実際のログの内容と一致する説明を生成した。実データでもって初めて、方法Bの参照CPDが「本物のcut-in」を正しくSATと判定できることを確認できた。

**方法C（統合モデル）**：このログ1本だけを`build_union_model`に渡すと、デフォルトの格子（`gx=5.0, gy=3.5`）のまま33個の圧縮状態に離散化され、モデルは31箱（ダミー開始箱含む）・`max_step=33`になった。membership check（自分自身が含まれるか）は6.50秒でSAT。ところが`count_scenarios`で列挙したところ、**1本の実ログだけから127個のシナリオが列挙された**（40.10秒）。これは方法Cにとって重要な発見である。原因は、実データの`rx`が完全に単調減少ではなく、合流後に`(0,4)→(0,3)→(0,4)→(0,5)→(0,4)→(0,5)→(0,6)→...`のように、粗い格子の同じセル（position=4やposition=5）を複数回行き来していたためである。同じ箱に複数の異なる遷移が出入りすることになり、モデル上は「そこで経路が分岐しうる」箱として扱われ、入力にはなかった組み合わせが多数生成されてしまう。合成ログ（増加・減少が単調になるよう手で書いたもの）では起きなかったこの現象が、実データでは1本だけでも起きることが分かった。これは11.2節の課題2「意図した一般化と意図しない一般化の区別」に直接関わる、実データならではの具体的な問題例であり、実データを本格的に扱うには、格子をさらに細かくする、あるいは小さな前後移動（ノイズ）を吸収する平滑化・ヒステリシスのような前処理を検討する必要があることを示している。

この節の実験は`logverify/demo_real_ajisai_log.py`（`python3 -m logverify.demo_real_ajisai_log <path-to-ajisai-log.json>`で実行）として実装した。AJISAIログ自体はBox配布でリポジトリには同梱していないため、パスを引数で渡す形にしている。1本の実データでの検証はできたが、11.2節課題1の「10本規模での検証」はまだ残っている。

**可視化**：このモデルは`max_step=33`と大きく、11.5〜11.7節で確認したEgoを同期させたワールド座標系アニメーション（`with_ego_track`ベース、strans使用）は、この規模では（`num_model=1`でも）タイムアウトした。そこで、Egoを固定参照点として描く単純な方式（11.3節、`gif_viz.render_scenarios_gif`）に`num_model`引数を追加し、`num_model=1`で1シナリオだけを描画したところ25秒程度で完了した。モデル構造図（11.4〜11.5節、`plot_model_with_ego_paper_style`）はz3による求解を伴わない純粋な描画処理のため、この規模でも1秒程度で問題なく生成できた。

**遠方をまとめてEgo同期版アニメーションを実用化**：上記のタイムアウトの原因は、一様格子（`gx=5.0`）のまま使ったため、`rx`が最大117mに達する遠方領域がまったくまとめられておらず、箱数31・`max_step=33`という大きなモデルになっていたことにある（11.6〜11.7節で導入した非一様格子`build_union_model_near_far_grid`を、このデモではまだ使っていなかった）。11.7節の`find_distinguishing_near_far_grid`による自動最大化探索は「複数ログを互いに区別できる範囲で遠方をまとめる」ものだが、**ログが1本しかない場合は区別すべき相手がいないため、この探索は際限なく粗い方向へ暴走し（実際に試すと箱数4・`max_step=4`まで潰れ、合流前の情報がほとんど失われる）、この用途には適さない**。そこで`auto_grid=False`を指定し、`rx_near_range=20m`（近距離・中距離帯はそのまま）、`rx_far_cell=15m`（遠方をやや粗くまとめる）を手動で選んだところ、箱数13・`max_step=13`まで縮小し、Egoを実際に同期させたワールド座標系アニメーションが17.95秒で生成できた（`real_ajisai_cutin_ego_sync.gif`）。実データについても、初めて「Egoが実際にCPDのcarとして前進する、論文と同じモデル化」でのアニメーションが得られたことになる。なお、この結果は非一様格子の「区別を保ったまま最大限まとめる」という自動化の仕組みが、複数ログを前提にした設計であり、単一ログではそのまま使えない（手動でパラメータを選ぶ必要がある）ことを示す具体例でもある。

### 11.9 実際のAJISAIログ複数本（6本）での検証

11.8節は実ログ1本だけの検証だったが、本節ではAJISAIデータセット（J-Storage/Box配布、`AJISAI/data/cutin/`フォルダ）から同じシナリオタグ（`road=non_intersection, position=ahead_right, direction=same_direction, behavior=cut_in`、`jama_summary.csv`で確認）を持つ実cut-inログを6本（`TD-NI-AR-SD-N04-CI-0030/0032/0035/0047/0067/0076.json`）選び、方法Cに複数本同時に投入した。11.2節課題1「実データ10本規模での検証」に向けた最初の複数本実験である。実装は`logverify/demo_real_ajisai_multi_log.py`（`python3 -m logverify.demo_real_ajisai_multi_log [log1.json log2.json ...]`、引数省略時は上記6本をデフォルトで使う）。

**前処理：シナリオ本題後の「その後の走行」の打ち切り**：6本中`TD-NI-AR-SD-N04-CI-0047.json`だけ、フレーム2546/3166以降、NPCがego進行方向に対しほぼ真横に90m以上も離れていく記録が続いていた（cut-in本体が終わった後、NPCが別経路へ折れたと見られる）。これをそのまま使うと、そのログ1本のためだけに格子・モデルが不必要に大きく広がる。そこで「`|ry|`（ego進行方向に直交する相対距離）が15mを超えたまま戻らなくなった時点」をシナリオ本題の終わりとみなして打ち切る前処理（`_trim_trailing_runaway`）を導入した。6本中5本はこの打ち切りの影響を受けない。これは11.8節で見つかった「実データはノイズを含む」という論点の、また別の具体例である。

**一様格子でのサイズ**：6本を`build_union_model`（一様格子、デフォルトのgx=5.0, gy=3.5）にそのまま投入すると、箱数74・`max_step=70`まで大きくなった。11.8節の1本だけの場合（31箱・`max_step=33`）でもmembership check・列挙に約6〜40秒かかっていたことを踏まえると、この規模でのSATソルブは相当に重くなることが予想され、実際に**membership check・シナリオ列挙は数分経っても完了しなかった**（打ち切った）。これは、11.7節で述べたEgo同期アニメーション特有の問題（strans由来の組合せ爆発）とは別に、素のmembership check・列挙そのものも、一様格子のまま複数の実ログを束ねると実用的な時間で終わらなくなりうることを示す、新しい知見である。

**非一様格子（近遠格子）で実用化**：6本のログに対して`find_distinguishing_near_far_grid`（`rx_near_cell=5.0, rx_near_range=20.0, gy=3.5`）を実行すると、遠方セルサイズは自動的に270.0mまで最大化された（複数ログが存在するため、11.8節で問題になった「単一ログでの際限のない暴走」は起きず、実際に6本を互いに区別できる範囲での最大値に収束した）。この格子で統合モデルを構築すると、箱数は74→15、`max_step`は70→14まで縮小し、

- membership check：6/6本ともSAT（4.74秒）
- シナリオ列挙：735個（6本の入力に対し、43.75秒）
- Ego同期ワールド座標系アニメーション（`num_model=5`）：132.82秒で生成完了

という結果が得られた。735という列挙数は入力の6本を大きく上回っているが、これは11.8節で確認した「実データのノイズによる同一セルの往復」が6本分重なった結果と考えられ、遠方セル270mというかなり粗い格子でもなお、近距離帯（`rx<=20m`、セル5.0m）側の解像度でこれだけの組み合わせが生まれることを示している。11.2節課題2「意図した一般化と意図しない一般化の区別」は、実データを複数本扱う場合にはより一層重要な課題になることが、この実験からも裏付けられた。

以上により、実データを複数本用いた場合でも、(a) 前処理でログ末尾の「その後の走行」のようなノイズを除去し、(b) 非一様格子（近遠格子）で遠方をまとめることで、方法Cのmembership check・シナリオ列挙・Ego同期アニメーションのいずれも実用的な時間で実行できることを確認した。11.2節課題1の「10本規模での検証」に対しては、6本という部分的な達成にとどまっており、AJISAIデータセットには同一タグのcut-inログが少なくとも59本以上（`jama_summary.csv`で確認した範囲、実際にはさらに多い可能性がある）存在することを確認済みなので、本数を増やすこと自体は容易である。ただし列挙数（735）が示すように、本数を増やすほど格子解像度と組合せ数のトレードオフはより厳しくなると見込まれ、今後の実験では「何本まで」「どの格子解像度まで」が実用的かを継続して確認していく必要がある。

### 11.10 参照モデルの抽象度への自動的な抽象化（方法B・単一ログ）

11.1〜11.9節での議論を経て、複数ログを箱共有で統合する方法Cの「一般化」は、健全性が証明されたオーバーアプローチメーションにはなっておらず（前掲の議論、格子・しきい値がいずれもヒューリスティックに選ばれているため）、モデリングにこだわるのであれば、分析したいviewpointを参照CPD（方法B）として最初に定義し、ログをその語彙に合わせて抽象化する方が筋が良い、という結論になった。本節はその最小の一歩として、複数ログの統合を行わず、**1本のログだけ**を対象に、「参照モデル自身の抽象度に、ログを自動的に合わせて抽象化できるか」を確認した。

これまでは、参照CPDの語彙（`reference_models.build_cutin_reference`の`i_range`=BEHIND(-1)/NEAR(0)/MEDIUM(1)/FAR(2)、`side_lanes`、`ego_lane`）と、生ログをその語彙に丸めるしきい値（`logverify.zones.ZoneThresholds`のnear_max/medium_max、横方向の格子幅gy）は、別々の場所（`build_cutin_reference`の呼び出しと`ZoneThresholds(...)`の呼び出し）で、デモスクリプトを書く人間が「値を合わせておく」ことに頼って指定されていた（11.8節の`demo_real_ajisai_log.py`参照）。値がずれても実行時まで気づけない。

そこで`logverify/reference_models.py`に`CutinReferenceScenario`（参照CPDモデルとその抽象化ルールを1つに束ねたデータクラス）と、そのファクトリ`build_cutin_reference_scenario(near_max, medium_max, gy, side_lanes, ego_lane, ...)`を追加した。このファクトリは、`build_cutin_reference`の`i_range`を常に`logverify.zones`のBEHIND/NEAR/MEDIUM/FARに固定するため、2つの語彙が食い違うことが構造的に起こらない。`CutinReferenceScenario.abstract(rel_xy)`は生の(rx, ry)系列をこの参照モデル自身の語彙に自動的に丸め、`CutinReferenceScenario.check(rel_xy)`は抽象化からmembership checkまでを1回の呼び出しで行う。

`logverify/demo_reference_scenario_abstraction.py`（`python3 -m logverify.demo_reference_scenario_abstraction [path-to-ajisai-log.json]`）で、実ログ`TD-NI-AR-SD-N04-CI-0035.json`（1697フレームの生の連続軌跡）を`ref.check(rel_xy)`に渡すだけで、参照モデルの語彙（近距離/中距離/遠距離×側方レーン/egoレーン）に自動的に丸められた4状態の圧縮列に抽象化され、そのままSAT判定・要約（11.8節と同じ結果）まで得られることを確認した。抽象化された(lane, zone)の値が参照モデルの語彙の外に出た場合は、`check_membership`が`unmatched_step`付きのUNSATとして検出する（`membership.py`の既存の仕組み）ため、「参照モデルの抽象度に合わせて自動的に抽象化できたか」自体も、この1回の呼び出しの中で検証されることになる。

複数ログへの拡張（方法Cの箱共有をやめた「シナリオのOR」としての統合）は、本節ではまだ扱っていない今後の課題である。

### 11.11 咲川氏のcut-in演算子を「判定そのもの」として直接使い、それ以外を完全に自由にする（v0.5）

11.10節の`build_cutin_reference_9area`は、咲川氏の抽象空間カットインルール（合流元はFOLLOWでない、合流先は必ずLEAD）をCPDの遷移制約として直接埋め込み、加えて「一度ego車線に入ったら隣接レーンへは戻れない」という制約（以下rule 3）を持っていた。しかしrule 3は、「カットインの前後の挙動は自由にしたい。カットインの後、さらにレーンを移動する場合も、参照モデルの作り方次第のはず」という要求と両立しない。

rule 3だけを単純に取り除き、合流遷移の制約（rule 2）だけを残す案も検討したが、これには問題がある。遷移をほぼ自由にした時点で、「一度も隣接レーンからego車線へ移らない（ずっとego車線に留まる）ログ」もこのグラフの中では当然SATになってしまうため、**SAT/UNSATという判定自体が、もはや「カットインが起きたか」の情報を一切持たなくなる**（SATであることはカットインの発生を何も保証しない）。つまり「遷移を自由にする」ことと「SAT/UNSATでカットインを判定する」ことは、原理的に両立しない。

そこで、以下のように役割を分離した:

- **参照CPDモデル（`reference_models.build_cutin_reference_9area`）**: もはやカットイン判定を一切行わない。咲川氏の9領域（lane×position、ego車両自身の物理サイズだけで決まる境界）を箱の語彙として使うだけの、ほぼ完全に自由な遷移グラフ（全ての箱同士が双方向に接続されている）にした。カットイン前・後（さらなる車線変更を含む）のどのような挙動も、この構造モデルの中で自由に表現できる。
- **カットイン判定そのもの（`logverify/sakikawa_relations.py`の新関数`detect_cutin`）**: 咲川氏の`abstract_cutin_detected`と全く同じ問い、すなわち「隣接レーンにいて後方ではない(position != FOLLOW)状態から、egoレーンの前方(LEAD)状態へ、隣接するステップ間で直接遷移した箇所が、圧縮済みの観測列のどこかに存在するか」を、SATを介さず、観測列に対する局所的・存在的なパターン照合として直接判定する。これは大域的な適合性（列全体が参照モデルの構造で説明できるか）を問うmembership checkとは異なり、「その特定のパターンが1箇所でも起きたか」だけを問う、局所的な演算子である。

`reference_models.build_cutin_reference_9area_scenario`が返すオブジェクトは、`.check(rel_xy)`（構造モデルに対するmembership。語彙の範囲内かどうかの弱いチェックであり、カットインの有無は保証しない）と`.detect_cutin(rel_xy)`（咲川氏の演算子を直接適用した、実際のカットイン判定）の両方を提供する。

`logverify/demo_sakikawa_cutin_operator.py`（`python3 -m logverify.demo_sakikawa_cutin_operator`）で、11.9節と同じ実ログ6本（0030, 0032, 0035, 0047, 0067, 0076）全てについて、`detect_cutin`による判定結果と、`vendor/trajectory_abstraction/src/abstraction_9area.py`自身の`abstract_cutin`判定結果を突き合わせ、**6本全てで一致すること**を確認した。特に0032・0047は、11.10節時点の（rule 3を持つ）モデルではUNSAT（合流後にさらに車線を移動しているため、rule 3に違反する）だったが、`detect_cutin`はこの2本についても咲川氏のツールと同じく正しく`True`（カットインあり）と判定する。カットイン後にさらにレーンを移動する挙動は、もはや構造モデル側では一切制約されないため、この2本のケースを扱うためだけの特別扱いは不要になった。

この設計は、9.5節以降で議論してきた「参照モデルの粒度・境界・どの性質を問うかは分析者が決める設計事項である」という結論とも整合している。「カットインという性質」は、SATという1つの判定基準に無理に押し込めるのではなく、その性質専用の演算子（今回は咲川氏の健全なルールをそのまま流用）で直接問う、というのが素直な設計であり、CPD/SATモデルの役割は「（カットインに限らない）一般的な語彙と構造」を提供することに限定される。

## 12. 方法Aによる衝突ログの原因分析（v0.6）

### 12.1 経緯：方法Aへの回帰、対象を衝突の原因分析に

11節までは方法B・Cの設計・検証が中心だったが、方法B（参照モデルの使い方）は検討中のため現状のまま保留し、方法C（複数ログの統合）も個別ログの原因分析結果をまとめる段階でこそ活きるため、これも現状のまま保留とし、まず**方法A（咲川氏の抽象化ツールで1本のログを直接抽象化する）**に立ち返って、**衝突の原因分析**に取り組むことにした。対象はAJISAIデータセットのcut-in（KSE2026論文によれば432トレース中93本が衝突を含む）。共有された論文（`KSE2026_.pdf`、AJISAIデータセット論文）を確認したところ、**衝突フラグ自体はAJISAIの配布物（`jama_index.json`, `jama_summary.csv`, sidecarの`*.jama.json`）のどこにも含まれていない**ことが分かった（road/position/direction/behaviorの4軸ラベルとconsistency_okのみ）。論文の「93/432が衝突を含む」という統計は、`groundtruth_size`（egoと各NPCのオリエンテッド・バウンディングボックスのサイズ）と`groundtruth_kinematic`（ワールド座標での位置・姿勢）を突き合わせて別途計算されたものと考えられる。

そこで、これまでMethod B/Cのデモで使ってきた6本のcut-inログ（0030, 0032, 0035, 0047, 0067, 0076）について、ego・NPCそれぞれのオリエンテッドバウンディングボックス（`groundtruth_size.vehicle_sizes`）のサイズを使い、egoの進行方向を基準にした相対座標(rx, ry)上で矩形同士が重なるフレームがあるかを直接判定したところ、**`TD-NI-AR-SD-N04-CI-0067.json`だけが実際に衝突（矩形の重なり）を含む**ことが分かった（フレーム761-793、t=149.509s〜150.293s、継続0.78秒、最大めり込み量0.255m）。他の5本は最小クリアランスが1.4m以上あり、衝突していない。既存の6本の中に対象が見つかったため、追加のダウンロードは不要だった。

### 12.2 咲川氏の9領域（粗い）抽象化では原因が見えない

`logverify/demo_collision_root_cause.py`で0067を咲川氏の9領域抽象化にかけると、開始から衝突を含む862フレームまでがずっと1つの状態`(lane=-1, position=+1)`（隣接レーン・前方）のままであり、衝突の瞬間に何が起きていたのかは全く見えない。これは「1697フレームを、カットイン直前・直後・離れている、のように見つけるのは難しい」というユーザーの当初の懸念が、実際にこの形で顕在化した例である。

### 12.3 重要な発見：咲川氏のlane境界は、衝突が起きてもなお「隣接レーン」と判定する

さらに重要なのは、咲川氏の`detect_cutin`（本ドキュメント11.11節）によるカットイン遷移`(lane=-1,position=+1)→(lane=0,position=+1)`が**フレーム863**で起きている、という事実である。すなわち、**衝突（フレーム761-793）はカットインが「成立したと判定される」フレーム863よりも前に、しかも完全に終わった状態で発生している**。これは、咲川氏のlane境界（`EGO_HALF_WIDTH`、すなわちego車両自身の車幅の半分だけを基準にする）が、**相手車両（NPC）自身の車幅を一切考慮していない**ために起きる。この衝突では、NPCの横方向オフセット`ry`は最も深いところでも-1.80m（ego車両の半車幅0.95mより大きい）であり、咲川氏の定義では「まだ隣接レーンにいる（`lane=-1`）」と判定され続ける。しかし、egoとNPC両者の車体幅を考慮した実際の矩形は、egoの半車幅(1.09m)とNPCの半車幅(0.97m)の合計(2.06m)よりも`|ry|`が小さくなった時点（この場合は約-2.06m未満）で重なり得るため、**「lane境界を跨ぐ前に、物理的な衝突が起こり得る」**。これは、9.5節で指摘した「距離と速度を独立に抽象化したことによるFP過多」とは逆の問題であり、**FN（見逃し）方向の問題**である：咲川氏のabstract_cutin/concrete_cutinルールは、自身の車体幅を考慮しない分だけ「まだカットインしていない」と判定しがちであり、その間に物理的な接触が起こり得ることを、この事例は具体的に示している。

### 12.4 EGO周辺を細かく刻んだ抽象化で、衝突までの過程を可視化

そこで`logverify/sakikawa_relations.py`に、9領域の枠組みは保ったまま**EGOのすぐ近くだけを細かく刻む**抽象化を追加した（`classify_fine`, `compress_to_fine_relation_states`, `fine_relation_states_from_relative_xy`）。単位はあくまで`EGO_HALF_WIDTH/n_bins`・`EGO_HALF_LENGTH/n_bins`（デフォルトn_bins=4）であり、分析用に選んだ恣意的なメートル値ではない（`max_range`引数で、何個分のego半車幅・半車長まで細分するかを指定し、それを超えたら9領域と同じく粗いまま飽和させる）。この抽象化を0067の衝突前後にかけると、

```
(lane_fine=-10, position_fine=+8)  frames 721-730
(lane_fine=-9,  position_fine=+8)  frames 731-732
(lane_fine=-9,  position_fine=+7)  frames 733-749
(lane_fine=-9,  position_fine=+6)  frames 750-752
(lane_fine=-8,  position_fine=+6)  frames 753-775
(lane_fine=-7,  position_fine=+6)  frames 776-789  <-- 衝突ウィンドウ
(lane_fine=-7,  position_fine=+7)  frames 790-797
(lane_fine=-6,  position_fine=+7)  frames 798-807
```

のように、NPCがEGOに向かって横方向に少しずつ近づいていく過程が、9領域では見えなかった段階的な変化として見えるようになる。

### 12.5 「なぜ」の分析：減速のタイミング・強さ、NPCの予測軌道のゆるさ

抽象化だけでは「なぜ」衝突したかは分からないため、`control_cmds`（ego制御コマンド）と`perception_objects`（NPCの予測経路`predict_paths`）を直接読んだ。

**減速のタイミングと強さ**：NPCの横方向移動（車線変更）開始は約t=148.11s。egoの減速指令（`control_cmds.longitudinal.acceleration`が負に転じる）もほぼ同時のt=148.11sから始まっており、**反応のタイミング自体は大きくは遅れていない**。しかし、そこから強い減速（-2 m/s²超）に達するまで約1.4秒かかっており（-1.0 m/s²到達が約148.44s、-2.0 m/s²到達が約149.0s、ピーク-2.55 m/s²が約149.73s）、**衝突ウィンドウ（149.51s開始）に入る時点でもまだ最大減速度に達していない**。ユーザーの仮説「減速のタイミングが遅かったり、その強さが弱かったりする」のうち、この事例では**タイミングよりも立ち上がりの弱さ（強さに達するまでの遅さ）が主因**と考えられる。

**NPCの予測軌道のゆるさ**：`perception_objects[].objects[].predict_paths`には、Autowareの予測モジュールが出力する複数候補の予測経路（各々`confidence`付き）が記録されている。NPCが実際に横方向移動を始めた後（t=148.11s以降）も、信頼度最大の予測経路は「このままレーンを維持して直進する」（`ry`がほとんど変化しない）という予測を出し続けており、実際の`ry`の変化（-2.4m台から徐々に0へ近づく動き）を予測できていない。同時に信頼度自体も1.0から0.2〜0.3まで低下し、候補経路の数も1個から5個に増えている（車線変更する/しないの複数仮説の間で予測が割れている状態）。これは、ユーザーが当初から立てていた仮説「NPCの予測軌道がゆるい」を、実際のログのデータで裏付けるものである。

### 12.6 まとめ

0067の衝突は、単一の原因ではなく、複数の要因が重なって生じている：(a) 咲川氏のlane境界が自車の車幅しか考慮しないため、「まだレーンを跨いでいない」と判定される間に物理的な接触域に入ってしまう（12.3節）、(b) egoの減速反応の開始タイミング自体は妥当だが、強い減速に達するまでの立ち上がりが遅い（12.5節）、(c) NPCの予測軌道が、実際の車線変更をリアルタイムに捉えきれず「まだ直進する」という予測にとどまり続ける（12.5節）。方法Aの粗い抽象化だけでは(a)は原因として見えず、(b)(c)は抽象化そのものではなく生データの直接分析でしか見えない、という点が、この事例分析全体を通じての教訓である。

実装は`logverify/sakikawa_relations.py`（`classify_fine`, `compress_to_fine_relation_states`, `fine_relation_states_from_relative_xy`）と`logverify/demo_collision_root_cause.py`（`python3 -m logverify.demo_collision_root_cause [path-to-log.json]`）。

今後の課題として、(1) 咲川氏のlane境界にNPC自身の車幅を加味した、より安全側（衝突を見逃さない）の判定への拡張、(2) 他の衝突ログ（cut-in以外の behavior、あるいは他パラメータのcut-inログ）でも同様の要因分析を行い、パターンを一般化できるかの確認、(3) 方法Cで複数の衝突ログの原因分析結果を横断的に集約する、が挙げられる（(3)は現時点ではまだ着手しない）。

### 12.7 衝突前後だけを細かくし、減速状態をアノテーションした「インスタンスCPD」（v0.7）

12.4-12.6節の分析結果を、CPD図そのものに落とし込んでほしいというユーザーからの要望があった。具体的には、(1) 衝突の近辺だけを細かく、遠方は粗いままにモデル化する、(2) 減速開始・減速強度の情報をCPDモデルにアノテーションとして直接書き込む、(3) EGOとNPCの振舞いが図の上で離れて描かれると両者の関係が分からないため、論文（`Scenario_Modeling_Language__Camera_Ready.pdf`）のスタイルに近づける、の3点である。

論文Fig.2/Fig.3/Fig.4を確認したところ、論文のCPDでは、車両ごとの箱が**同じ列に、共通のPOSITION値（時間的に何番目の遷移か、ではなく、両者が比較可能な位置にあることを示す整数）で揃えて**配置されている（例: `Pos(LCar(1))=Pos(RCar(1))=1`）。一方、既存の`model_diagram.plot_model_with_ego_paper_style`（方法Cで使用）は、NPC側のスイムレーンを「(lane, position)の値の順位」で、Ego側のスイムレーンを「ステップ番号」で列を割り当てており、**この2つの列軸の意味が異なる**ため、同じ列に並んでいても同じ瞬間を表すとは限らない。これが「EGOとNPCの振舞がCPDで離れていると関係がわからない」という指摘の技術的な原因だった。

そこで、複数ログにまたがる一般的な参照モデルではなく、**1本のログ専用の「インスタンスCPD」**（9.2節で導入した用語）として、新しく`logverify/collision_cpd_diagram.py`を作成した。この図は、

- **列 = そのログで実際に起きた箱の遷移順**（時間順）とし、NPC側のスイムレーンとEgoの挙動スイムレーンの両方が、この同じ列軸を共有する。つまり、あるNPCの箱の真上に描かれるEgoの箱は、必ず「同じ時間区間」のEgoの状態を表す（両者を薄い点線で結んで明示）。
- **行 = NPC側は「隣接レーン（側方）」「ego車線」の2スイムレーン**（咲川氏のlane境界`EGO_HALF_WIDTH`を基準に振り分け）+ **Ego側は「Ego（自身の挙動）」の1スイムレーン**（背景色付きで、巡航／減速開始／減速中／強い減速の4状態のいずれかと、実際の加速度値を表示）。
- 衝突が起きた箱は赤枠・赤背景で強調し、「減速指令開始」「強い減速(-2m/s²超)到達」「NPC予測が直進継続を予測し続けている（信頼度低下）」といったイベントを、該当する箱に吹き出し注記として直接書き込む。

格子の細かさは、12.4節の`compress_to_fine_relation_states`とは別に、`logverify/grid_bridge.compress_to_grid_states_variable`（near/far可変格子）を、この図専用に非常に細かく調整したパラメータ（`RX_NEAR_CELL=1.0`, `RX_FAR_CELL=50.0`, `RX_NEAR_RANGE=15.0`, `GY=0.3`）で使用した。rx（進行方向）はego近傍（`|rx|<=15m`）だけ1mセルで細かく、それより遠くは50mセルでまとめて1つの粗い箱にする。ry（横方向）はもともと変動範囲が数mしかないため、遠方でも一様に0.3mセルの細かいままにしている（粗くする恩恵が小さいため）。この結果、0067の全34箱のうち、遠方走行中の区間（フレーム0-615）と合流後に十分安定した以降の区間（フレーム1358-2552）はそれぞれ1つの粗い箱にまとめられ、衝突前後（フレーム616-1357）だけが22個の細かい箱として描かれる。

実装・可視化の過程で見つかった注意点（いずれも`logverify/demo_collision_cpd_annotated.py`で対応済み）：

- **粗くまとめた箱のEgo状態を、区間内の最小加速度で決めると誤る**: 遠方走行中の箱（フレーム0-615）は、区間の途中（ログ冒頭、t≈130.48s付近）にカットインとは無関係な一時的減速スパイク（-1.5 m/s²、シミュレーション開始直後の整定挙動と見られる）を含んでおり、これを区間内の最小値としてEgo状態に採用すると「減速中」という誤ったラベルになる。粗い箱については、区間の最小値ではなく**区間の終端（次の箱に引き継がれる瞬間）に最も近い値**を使うよう修正した（`ego_state_at(..., use_endpoint=True)`）。
- **減速イベントの検索も同じ初期スパイクを拾ってしまう**: 「減速指令開始」を`control_cmds`全体から検索すると、上記のt≈130.48sのスパイクが最初にヒットしてしまう。遠方走行中の粗い箱が終わった時刻以降だけを検索対象にすることで回避した。
- **複数のイベント注記が同じ箱に重なる**: 「強い減速到達」と「NPC予測のゆるさ」の注記が同じ箱（衝突箱の2つ手前）に付く場合、そのまま描画すると重なって読めなくなる。箱ごとに何個目の注記かを数え、縦方向にずらして積み上げるようにした。

生成された図（`out_gif/collision_0067_cpd_annotated.png`）は、左から順に「巡航→減速開始」の箱（"減速指令開始"の注記付き）、衝突を含む赤枠の箱群（"強い減速"・"NPC予測"の注記付き）、隣接レーンからego車線への遷移、合流後に安定する粗い箱、という流れが、EgoとNPCの挙動を同じ列で対応づけたまま一望できる。方法Cの一般モデル用GIF（12.4節以前から使っている`render_world_frame_gif`ベースのアニメーション）と役割は異なり、こちらは「なぜこの1本のログで衝突が起きたか」を静的な1枚のCPD図として説明することに特化している。

### 12.8 横方向オフセット(ry)そのものを縦位置にした版（v0.8）

12.7節の図は、NPCの箱を「隣接レーン（側方）」「ego車線」という2つの固定スイムレーンに振り分けるため、あるスイムレーン内でNPCがEgoにどれだけ横方向に近づいているかは、箱の中の文字ラベル（`k=-7`等）でしか分からなかった。ユーザーから「横方向がわからない、横方向も詳細化して衝突の様子がわかるようにしてほしい」との指摘があり、これに対応した。

`logverify/collision_cpd_diagram.py`に新しい描画関数`plot_instance_cpd_lateral`を追加し、NPCの箱の**縦位置そのものを、実際の横方向オフセット`ry`（メートル）に比例させる**ように変更した。具体的には、各箱について代表フレーム（細かい箱は区間の中間フレーム、遠方・合流後の粗い箱は隣の細かい箱に引き継がれる側の端のフレーム）の`ry`値を`InstanceBox.ry_m`として保持し、それを縦座標に使う。これにより、NPCが時間とともに横方向にEgoへ近づいていく様子が、箱の折れ線としてそのまま目に見えるようになった（`k`という格子インデックスの単調な変化を、物理的な距離の変化として直接読み取れる）。

さらに、12.3節で発見した「咲川氏のlane境界（ego自身の車体半幅だけを基準にする）は、相手車両の車体幅を考慮しないため、物理的な接触が起こり得る範囲より内側でしか『同じレーン』と判定しない」というギャップを、この図の上に**2種類の水平の帯・線として直接重ねて**表示した。

- **ego車線帯**（緑の帯、`|ry| <= ego_half_width`）: 咲川氏のlane境界そのもの。
- **接触境界**（赤の破線、`|ry| <= ego_half_width + npc_half_width`、両車の車体半幅の和）: これを跨ぐと物理的な接触が起こり得る境界。0067では±2.06m。

衝突として赤枠で強調されている箱（k=-7,i=4〜k=-6,i=5）は、この図の上で**ego車線帯（緑）の外側にありながら、接触境界（赤破線）のすぐ内側**に位置しており、「lane境界を跨ぐ前に、接触境界を跨いで衝突が起きている」という12.3節の発見が、テキストではなく図形として一目で分かるようになった。Ego自身の挙動（巡航／減速開始／減速中／強い減速）は、12.7節の図と同様、一番上の固定スイムレーンにNPCの箱と同じ列で描き、両者の関係も維持している。

実装は`logverify/collision_cpd_diagram.py`（`InstanceBox.ry_m`, `plot_instance_cpd_lateral`）と`logverify/demo_collision_cpd_annotated.py`（`vehicle_half_widths`、`build_boxes`が各箱に`ry_m`を設定する部分、`run`が`plot_instance_cpd_lateral`も呼び出す部分）。出力は`out_gif/collision_0067_cpd_lateral.png`（12.7節の図`collision_0067_cpd_annotated.png`とは別ファイルとして、両方を残している）。

### 12.9 12.7/12.8節の図を、正式な`gcpd.Model`として構築する（v0.9）

12.7・12.8節の図は、いずれも`logverify/collision_cpd_diagram.py`独自の描画ロジック（matplotlibで箱を手で並べる）であり、`gcpd.py`が定義する正式なCPDモデル（Z3上のBox/Pos/Lane関数、`gcpd.add_trans`等のSAT制約）そのものではなかった。ユーザーから「これをgcpdのモデルとしてつくれますか」との依頼があり、12.7/12.8節と全く同じ細かいnear/far格子（`RX_NEAR_CELL=1.0, RX_FAR_CELL=50.0, RX_NEAR_RANGE=15.0, GY=0.3`）を使って、log 0067だけを表す正式な`gcpd.Model`を構築した。

使ったのは方法C（`logverify/multi_log_model.py`）の`build_union_model_near_far_grid`である。方法Cは本来「複数ログを1つのモデルに統合する」ためのものだが、入力を`[rel_xy]`という**1本のログだけ**にすることで、本質的には方法A（咲川氏のツールで1本のログを直接抽象化する「インスタンスCPD」）と同じ役割を、方法Cの機械（`gcpd.Model`の構築・membership checkによるSAT確認・シナリオ列挙）を流用して達成できる。

`logverify/demo_collision_gcpd_model.py`（`python3 -m logverify.demo_collision_gcpd_model`）を作成し、以下を確認した。

- 構築されたモデルは、ダミー開始箱を含めて**箱数51、max_step=65**。
- `verify_logs_included`によるmembership check（SAT）: **True**（22.6秒）。すなわち、このモデルはlog 0067自身の箱列を正しく受理する、正式なCPDモデルとして構築できている。
- 箱列（65個の圧縮状態）を調べると、`GY=0.3m`という非常に細かい格子のため、NPCの横方向の位置がわずかに揺れ戻る箇所で、**同じ格子セル(lane, position)を時間的に離れた2箇所以上で再訪している**（例: `(0,10)〜(0,15)`の範囲を2回通過、`(-9,16)`等も同様）。これは、単一ログから作ったモデルであっても、格子が細かすぎると（測定ノイズや実際の微小な揺れ戻りを拾って）本物の分岐・合流点が生じ得る、という11.2節で既に指摘していた問題（「データのノイズに対して格子が細かすぎることによる意図しない一般化」）が、単一ログでも起こりうる具体例である。
- この分岐・合流のため、`count_scenarios`（全シナリオ数の列挙）と、Ego同期ワールド座標系GIF（`render_world_frame_gif`、strans同期遷移をSATで解く）はいずれも数分経っても終わらず、今回は省略した。これは11.6/11.7節で報告した「モデルの分岐が多いほどEgo同期アニメーションのSAT求解が重くなる」という既知の傾向と一致する。membership checkは分岐の有無によらず軽い（1本の箱列をなぞるだけ）ため、問題なく完了している。
- モデルの構造そのものは、既存の`model_diagram.plot_model_with_ego_paper_style`でも描画できることを確認した（`out_gif/model_collision_0067_gcpd_fine.png`）。ただし、この図は12.7節で指摘した「NPC側は(lane,position)の順位、Ego側はステップ番号という、意味の異なる列軸を使っている」という制約をそのまま引き継いでいる（方法Cの既存ツールの汎用的な構造図であり、12.7/12.8節で作った、同じ列軸を共有する見やすい版とは別物）。

まとめると、12.7/12.8節の分析結果は、単なる手書きの可視化ではなく、**方法Cの機械を1本のログに限定して適用することで、正式なgcpd.Model（Z3で解けるCPD）としても構築・検証できる**ことが分かった。ただし、衝突近辺を捉えるための細かい格子（特にGY=0.3mという横方向の細かさ）は、単一ログでも実際のノイズを分岐点として拾ってしまうため、このモデルをEgo同期GIFやシナリオ列挙に使うには格子を粗くする（分岐点を減らす）か、SAT側の高速化が必要になる、という新たな課題が見つかった。

実装は`logverify/demo_collision_gcpd_model.py`。既存の`logverify/multi_log_model.py`（`build_union_model_near_far_grid`, `verify_logs_included`, `count_scenarios`）と`logverify/model_diagram.py`（`plot_model_with_ego_paper_style`）、`logverify/world_frame_gif.py`（`render_world_frame_gif`）を変更なしでそのまま再利用しており、新規のCPD構築ロジックは追加していない。

今後の課題として、(1) 分岐点を許容しつつシナリオ列挙・Ego同期アニメーションを実用的な時間で終わらせる方法（格子を部分的に粗くする、SATソルバーへのヒント追加、列挙の打ち切り等）の検討、(2) 逆に「単一ログのモデルに分岐が生じること自体」を、ノイズ検出やログの品質チェックに積極的に使えないかの検討、が挙げられる。

### 12.10 ノイズ除去の抽象化（ヒステリシス、v0.10）

12.9節で見つかった分岐点（`(-10,16)`, `(0,10)〜(0,15)`等の再訪）について、ユーザーから「ノイズ除去の抽象化ができますかね」との依頼があった。実際にログの生データ（rx, ry）を確認したところ、分岐点には2種類の性質の異なるものが混在していることが分かった。

- **本当にノイズと呼べるもの**（例: `(-10,16)`, `(-9,16)`, `(-9,17)`付近の再訪）: NPCの横方向位置(ry)が、格子セルの境界ちょうどの位置に留まり、わずかな測定ノイズ（あるいは実際の1〜数十cm程度の揺れ）でセルの内外を何度も往復している。
- **物理的に実在する挙動**（例: `(0,10)〜(0,15)`付近の再訪）: 実際にrxの値を追跡すると、合流後にNPCがEgoから一旦約10m離れ、再び約10m近づく、という現実の追従挙動（車間距離の緩やかな揺れ戻り）が起きていた。これは測定ノイズではなく、同じ格子セルを2回通る本物の物理的往復である。

この区別に基づき、前者（格子境界ちょうどでのチャタリング）だけを吸収する、**ヒステリシス（シュミットトリガー）付きの格子量子化**を`logverify/grid_bridge.py`に実装した。

- `hysteresis_filter_indices(values, idx_fn, margin)`: 値について単調非減少な任意の格子インデックス関数（`grid_index_centered`や`grid_index_variable`のどちらにも使える汎用実装）に対し、「現在のセルの境界から`margin`だけ余分に踏み出さない限り、セルを移らない」という制約を課す。直近に安定していた値と新しい値の間で、実際に格子インデックスが切り替わる境界点を二分探索で求め、そこからの超過量で判定する。
- `to_grid_indices_variable_hysteresis` / `compress_to_grid_states_variable_hysteresis`: これを近傍/遠方可変格子のrx・ryそれぞれに適用し、従来の`compress_to_grid_states_variable`と同じ形（`GridState`のリスト）で圧縮状態を返す、ドロップイン置換。

0067の同じ細かい格子（`RX_NEAR_CELL=1.0, RX_FAR_CELL=50.0, RX_NEAR_RANGE=15.0, GY=0.3`）に、余裕率`margin_ratio=0.3`（セルサイズの30%を境界超過の必要量とする）のヒステリシスを適用した結果:

| | 箱数 | 分岐点(重複) |
|---|---|---|
| ヒステリシスなし | 65 | `(-10,16), (-9,16), (-9,17), (0,10)〜(0,15), (1,15), (2,17), (3,17)` （12個） |
| ヒステリシスあり | 54 | `(-9,17), (0,10)〜(0,15)` （7個、いずれも本物の物理的往復） |

境界チャタリングによる分岐点は完全に除去され、残ったのは実際に物理的な往復が起きている箇所だけになった（`(0,10)〜(0,15)`は前述の合流後の車間距離の揺れ戻り、`(-9,17)`も同様に遠方での実際の速度差による一時的な接近・離反）。この結果は「ノイズによる見せかけの分岐」と「データが正しく捉えている本物の分岐」を区別できることを示しており、後者を無理に消してしまうと実際の挙動（合流後も車間距離が安定しない、といった重要な情報）を失うことになるため、意図的に残している。

**注意点**: ヒステリシスの余裕率(`margin_ratio`)を大きくしすぎる（試しに桁違いに大きくした場合）と、遠方領域（`rx_far_cell=50m`）のような広いセルでも、本来必要な前進さえ「ノイズ」として吸収してしまい、抽象化が過度に粗くなる危険がある。今回`margin_ratio=0.1〜0.5`の範囲で試したところ、いずれも0067の主要な分岐点除去の効果はほぼ同じであり、結果は範囲内で安定していた。

実装は`logverify/grid_bridge.py`（`hysteresis_filter_indices`, `to_grid_indices_variable_hysteresis`, `compress_to_grid_states_variable_hysteresis`）と`logverify/multi_log_model.py`（`build_single_log_model_hysteresis`、1本のログからヒステリシス付きでgcpd.Modelを構築する）。

### 12.11 車両サイズからの自動格子導出（v0.11）

もう一つのユーザーからの依頼「このように重要なところだけ細かく、それ以外は粗くといった自動詳細化はできますか」に対応した。12.7〜12.9節で使ってきた近傍/遠方格子のパラメータ（`RX_NEAR_CELL=1.0, RX_FAR_CELL=50.0, RX_NEAR_RANGE=15.0, GY=0.3`）は、実際にはlog 0067を見ながら「これくらいが良さそうだ」と手で選んだ値であり、12.4節（`classify_fine`）以来の「分析用に選んだ恣意的なメートル値ではなく、車両自身の物理サイズを単位にする」という一貫した方針から外れていた。

そこで、新しいモジュール`logverify/auto_grid.py`で、この4つのパラメータを`groundtruth_size.vehicle_sizes`（ego・NPCそれぞれの半車幅・半車長）から自動的に導出できるようにした。

- `auto_gy`: 咲川氏のlane境界と同じ考え方（`EGO_HALF_WIDTH`を`n_bins`分割）で横方向セルサイズを求める。
- `auto_near_range`: 12.8節の接触境界（`ego_half_width + npc_half_width`）と同じ発想を縦方向の車体サイズに適用し、両者の半車長の和の`near_range_factor`倍を「近傍」とする。
- `auto_near_cell`: 両者の半車長の和を`near_cell_bins`分割し、近傍の縦方向セルサイズとする。
- `auto_far_cell`: 近傍の外側は`near_range`の`far_cell_factor`倍という粗いセルにまとめる。

0067の車両サイズ（ego半車長2.443m・半車幅0.95m、NPC半車長2.32m・半車幅0.97m）から、デフォルトのビン数・倍率（`n_bins=3, near_range_factor=3.0, near_cell_bins=5.0, far_cell_factor=5.0`）で自動導出した結果は、`gy=0.364m, rx_near_cell=0.953m, rx_near_range=14.289m, rx_far_cell=71.445m`となり、手で選んだ値（`0.3m, 1.0m, 15.0m, 50.0m`）といずれも近い範囲に収まった。これは、この物理サイズに基づく自動導出方法が、その場しのぎの値選びではなく合理的であることの傍証である。

さらに、この自動導出パラメータに12.10節のヒステリシス（`margin_ratio=0.3`）を組み合わせたところ、箱数55→45（ダミー開始箱を含めると40）に減り、分岐点は`(-8,16), (0,11)〜(0,15)`の6個（うち`(0,11)〜(0,15)`は12.10節で確認した本物の物理的往復）まで減少した。この自動格子＋ヒステリシスで`logverify/multi_log_model.py`の`build_single_log_model_hysteresis`を使ってgcpd.Modelを構築したところ、箱数40・max_step=45（ダミー開始箱含む）となり、membership checkはSAT（約10秒、12.9節の51箱・65ステップのモデルの22.6秒より高速化した）。

以上により、「重要なところ（衝突が起こりうる近傍）だけ細かく、それ以外は粗く」という詳細化のパラメータ自体を、分析者がログを見ながら手で調整するのではなく、車両の物理サイズという客観的な基準から自動的に導出できることを確認した。

実装は`logverify/auto_grid.py`（`auto_gy`, `auto_near_range`, `auto_near_cell`, `auto_far_cell`, `auto_grid_params`, `auto_grid_params_from_ajisai`）と`logverify/demo_auto_grid.py`（`python3 -m logverify.demo_auto_grid`、手動格子と自動格子・ヒステリシスあり/なしの4通りを比較する）。

今後の課題として、(1) `n_bins`・`near_range_factor`等のビン数・倍率自体も、複数の衝突ログを使って妥当な値を経験的に決める（現状はclassify_fineや接触境界の考え方を援用した初期値）、(2) ヒステリシスの`margin_ratio`も同様に、より多くのログでの検証を経て標準値を決める、(3) 12.9節で見つかった「シナリオ列挙・Ego同期GIFが遅い」問題が、分岐点の削減（本節）でどこまで改善するかを実測する、が挙げられる。

### 12.12 原因を直接語る抽象値による「抽象解釈」（v0.12）

ここまでの方法A（12.1〜12.11節）は、rx・ryという連続値を格子で区切って「箱」に離散化する抽象化であり、格子を細かくするほど元の値に近づくが、格子のインデックス自体（`k=-7`等）は「なぜ悪かったか」を直接語らない。ユーザーから「衝突の原因がわかる抽象度に自動的に抽象化したい．抽象化したモデルでは，それに現れている要素を見れば，原因が特定できるものが出現していてほしい．例えば，実際の速度ではなくて，速すぎる等の抽象的な値である．…咲川さんがcut-in演算子に関しては，抽象値で演算子に解釈を与えていると思います．同じような感じです」との依頼があった。

咲川氏のcut-in演算子（`detect_cutin`、11.11節）は、(lane, position)という抽象値の上で隣接レーンからego車線への遷移パターンを直接判定する演算子であり、生のrx/ryを見ているわけではない。この発想を「原因」の軸に適用し、新しいモジュール`logverify/abstract_cause.py`に、3つの抽象解釈演算子を実装した。

1. **`classify_deceleration_adequacy`（減速の十分性）**: 生の加速度値をそのまま使うのではなく、「その状況で衝突を避けるために本来必要だった減速度」（`required_deceleration_magnitude`、教科書的な制動距離の式`v^2/(2d)`で運動学的に導かれる、これも恣意的な値ではない）に対する実際の達成値の比(ratio)で、{不要, 過剰, 適切, 弱い, 非常に弱い}に分類する。
2. **`classify_prediction_reliability`（NPC予測経路の信頼性）**: `predict_paths`が予測した横方向変化と実際に起きた変化の符号・大きさ、および信頼度(confidence)を組み合わせて、{的確, 低信頼, 陳腐（自信満々の誤り）}に分類する。
3. **`classify_contact_margin`（横方向の接触余裕）**: 12.8節の接触境界（両者の車体半幅の和）を単位とした比`|ry|/(ego_half_width+npc_half_width)`で、{余裕, 接近中, 接触可能, 接触}の4段階に分類する（12.8節の2値をordinalに拡張したもの）。

`logverify/demo_abstract_cause.py`（`python3 -m logverify.demo_abstract_cause`）で0067に適用した結果:

- **接触余裕**は、フレーム561〜760で「接近中」、衝突ウィンドウ(761-793)で「接触」、その後「接触可能」へときれいに遷移し、生のry値を見なくてもこの抽象値の遷移だけで衝突の瞬間が特定できることを確認した。
- **予測信頼性**は、カットイン検出(t=148.11s)から衝突ウィンドウ開始(t=149.51s)にかけて、一貫して「低信頼」（confidence≈0.22）と分類された。これは12.5節で述べた「信頼度が1.0から0.2〜0.3に低下する」という記述のうち、**この特定の区間ではすでに信頼度が下がりきった後**であることを示しており、12.5節の記述をやや精緻化する結果になった（confidenceが高いまま予測を外し続ける、より危険な「陳腐」状態は、この区間より前に起きていた可能性がある）。
- **減速の十分性**は、カットイン検出時点のスナップショットで評価すると「過剰」（達成減速度2.44 m/s² > 必要減速度1.40 m/s²）という、12.5/12.6節の「立ち上がりが遅い」という結論と矛盾するように見える結果になった。原因を調べたところ、`required_deceleration_magnitude`は`v^2/(2d)`という式の性質上、評価する瞬間の縦方向の残り距離(d)にきわめて敏感であり（実際にdを4フレームおきに動かして再計算すると、「非常に弱い」「弱い」「過剰」が数百ミリ秒の間に入れ替わる不安定な挙動を示した）、**1時点のスナップショット比較では、いつその時点を選ぶかによって結論が変わってしまう**ことが分かった。これは演算子の設計上の欠陥であり、今後の課題として、瞬間値の比較ではなく、接近区間全体にわたる`required(t)`と`achieved(t)`の推移を比較する（例: 「一定時間以上、達成値が必要値を下回り続けた区間があるか」のような時間積分的な判定）時間的に頑健な演算子への改良が必要である。

この結果は、「抽象解釈の演算子をどう設計するかによって、原因の見え方が変わりうる」という、抽象解釈という手法そのものの本質的な難しさを具体的に示す事例でもある。接触余裕・予測信頼性の2つは、生データの単純な比較（符号・信頼度）に基づくため頑健に機能したが、減速の十分性は、物理量の非線形性（距離0付近での発散）のために、演算子自体の設計をもう一段丁寧に行う必要がある。

**CPDへの組み込み方針（今後）**: これら3つの抽象値は、現状は`logverify/collision_cpd_diagram.py`のインスタンスCPD（12.7節）の`ego_state`と同様、箱に付随する注釈として扱うのが最も手軽である。より踏み込んで、SATで検証可能な性質として扱いたい場合は、`gcpd.py`の`Pos`・`Lane`と並ぶ新しいZ3関数（例: `DecelAdequacy(car, box)`, `PredReliability(car, box)`）を追加し、各箱に付随する属性として`gcpd.Model`に組み込むことが考えられる（1本のログのインスタンスモデルでは状態数はログの実際の遷移数のままなので、分岐が増えるわけではない）。

実装は`logverify/abstract_cause.py`（`required_deceleration_magnitude`, `classify_deceleration_adequacy`, `classify_prediction_reliability`, `classify_contact_margin`）と`logverify/demo_abstract_cause.py`。

今後の課題（分析のアイデア、会話内で提示したものを記録）:

1. **反例駆動の演算子改良**: 12.12節で見つかった「減速の十分性」演算子の不安定さを、時間積分的な判定に置き換えて再検証する。
2. **多数の衝突ログでの一般化**: KSE2026論文によれば432トレース中93本が衝突を含む。0067以外の衝突ログにもこの3演算子を適用し、「接触余裕が接触可能に達した時点で、減速の十分性・予測信頼性がどちらも悪化しているか」という組み合わせパターンが一般に成り立つかを確認する。
3. **原因の分類（フォールト・ローカライゼーション）**: 複数の衝突ログについて、3つの抽象値のうちどれが最初に「悪化」したか（減速起因／予測起因／両方）で衝突ログを分類し、原因のタクソノミーを作る。
4. **反実仮想（counterfactual）分析**: gcpd.Modelの中で、ある箱の抽象値（例: 減速の十分性）を仮に「適切」に置き換えたら、`ps_col`（9.4節の衝突述語）がUNSATになるか（＝その要因を修正すれば衝突を避けられたか）をSATソルバーで確認する、要因ごとの寄与度分析。
5. **時相論理的な性質のチェック**: 「接触余裕が接触可能に達する前に、必ず予測信頼性が陳腐または低信頼になっている」といった、CTL/LTL風の性質を、SAT/gcpd.Modelの枠組みで（あるいは圧縮済み状態列に対する直接のパターン照合で）検証する。11.11節のdetect_cutinと同じスタイル（局所的な存在パターン照合）で実現できる可能性が高い。
6. **感度分析**: `overkill_ratio`, `confidence_threshold`, `approach_ratio`等の演算子内の閾値（比）を振って、分類結果がどこまで安定か（閾値のちょっとした変化で「弱い」が「適切」に変わってしまわないか）を確認する。

### 12.14 位置関係のスナップショット列としての可視化（v0.14, CPDの箱列そのものを描く）

ユーザーから次の指摘があった。「シナリオベース分析なので、CPDのような位置関係の上に抽象値を割り当ててください。例えば添付したようなEGOとNPCの位置関係（dx0, dy0, Ve0, Vy, Vo0のような図）です。これをスナップショットとすると、そのスナップショットが列を成した感じのものを作ってください。CPDはそれをモデルとして表現したものです。スナップショットの列がCPDで列挙したものになっている関係です。」

これは12.13節への重要な訂正である。12.13節は「実時間」を横軸にとり、生データのサンプリング間隔ごとに抽象値を並べたものだった。しかしユーザーが求めているのは、**CPDの箱そのもの**を1列に並べ、各箱を「その箱を代表する瞬間のEGO・NPCの位置関係の模式図」として描いたものである。すなわち、スナップショット列とCPDの箱列は同じものの2つの見方であり(スナップショット列 = CPDが列挙する状態遷移列の絵)、両者が1対1に対応していなければならない。

- 12.12節の3つの抽象解釈演算子（減速の十分性・NPC予測の信頼性・接触余裕）の分類結果（色付きラベル）

を1枚のパネルとして描き、パネルを箱の順番（=時間順）に矢印でつないで横一列に並べる。衝突が発生している箱（接触余裕＝「接触」）はNPCの矩形を赤くして目立たせる。

0067に適用した結果（`out_gif/collision_0067_scenario_snapshots.png`）では、box#8〜#18の11枚のパネルが、NPCが横方向に接近しながら（dy0が-2.87mから-1.24mへ単調に縮小）EGOの前方へ回り込み、box#15（t=+2.19s、接触余裕＝「接触」）でNPCの矩形が赤くなる、という一連の流れが、生の数値を追わなくても位置関係の絵として一目で読み取れる。減速の十分性ラベルは、box#8〜#13までは「非常に弱い」「弱い」と推移し、box#14以降で12.12節・12.13節で指摘した不安定さにより唐突に「過剰」へ切り替わる——この様子も、他の2つの抽象値・幾何学的な位置関係と並べて見ることで、「なぜ他の抽象値は衝突直前まで悪化を示し続けているのに、この演算子だけ唐突に方向が変わるのか」という疑問がより具体的な形で浮かび上がる。

### 12.15 抽象化関数（しきい値）の自動合成——Bensalem/Lakhnech/Owre [CAV'98] とSMTによるアプローチ（v0.15）

ユーザーから、抽象解釈演算子（12.12節）のしきい値（`overkill_ratio`等）について次の質問があった。「これらの抽象的な値は，速度とかの具体的な値をデータマッピングを用いて抽象化していると思います．そのようなデータマッピングする抽象化関数を自動的に求めることは可能でしょうか？例えば，添付の論文にあるような方法を使えると思います．PVSのかわりにSMTを使います．」（添付論文: Bensalem, Lakhnech, Owre, "Computing Abstractions of Infinite State Systems Compositionally and Automatically", CAV'98）。

**論文の方法の要点と、本プロジェクトの問題との違い。** 論文のelimination methodは、抽象化関数α（具象変数Cと抽象変数Aの上の述語）が**すでに与えられている**という前提のもとで、「Sᶜ ⊑ᵅ Sᵃ（SᵃがSᶜの安全な抽象化である）」を保証する抽象遷移関係Rᵃを、全関係（universal relation）から出発して安全に消去（eliminate）していくことで自動計算する方法である。消去できるかどうかの判定は、Hoare tripleの妥当性判定 `α⁻¹(s₀ᵃ) ⇒ wp(Rᶜ, Σᶜ \ α⁻¹(s₁ᵃ))` に帰着し（Lemma 3）、論文ではこれをPVSの定理証明器で証明している。これはSMT（Z3）のUNSATチェックに直接置き換えられる、汎用的な考え方である。ただし論文自身、αそのものの自動生成については「ガード中の原子論理式をそのままブール変数にする」という粗い既定の方法（脚注4、[13]の方法の引用）しか提供しておらず、これは論文も「一般に粗すぎる」と述べている。すなわち、**論文が自動化しているのは「与えられたαについて、安全な抽象遷移関係を導く」ことであり、「原因を語るのに適したαそのもの（しきい値というデータマッピング）を新規に発見する」ことではない**。

そこで、ユーザーへの追加確認「衝突を起こす要因が与えられれば，それらから自動的に求まりますか？」を踏まえ、次のような制約ベースのしきい値合成を`logverify/synth_abstract_thresholds.py`として実装した:

1. **既知の原因を、Z3への制約として与える。** 12.5〜12.6節ですでに確立している結論——log 0067の衝突は、EGOの減速がカットイン検出から衝突直前まで一貫して「弱いまま」だった（緩やかな立ち上がりであり、衝突直前に急に「過剰」になったのではない）——を、12.14節のCPDの箱列（box#8〜#13、衝突ウィンドウ直前まで）それぞれについて「『適切』以上に分類してはならない」という制約として与える。
2. **Z3のOptimizeで、既定のしきい値（`overkill_ratio=1.5, adequate_ratio=1.0, weak_ratio=0.5`）からの変化が最小になるしきい値を求める。** 単に制約を満たすしきい値を1つ見つけるだけでなく、「今すでに人間が選んでいるしきい値に対する最小限の補正」として合成することで、任意の解ではなく既存の設計との整合性を保った解を得る（Real変数の絶対値をL1距離として`opt.minimize`する。厳密な"<"制約はZ3のOptimizeでは下限が達成されない開集合になり最適化が不安定になるため、`ratio + margin <= threshold`という閉じた制約に変換している）。
3. **この際、12.12/12.13節の不安定さの真因が判明した。** 単一フレームでの評価をやめ、**その値が属するCPDの箱（`GridState`）の区間全体**をclosing_speed・achievedの平均化ウィンドウとして使う（`abstract_cause.box_aggregated_deceleration_ratio`）と、box#8〜#13のratioはすべて0.03〜0.48の範囲に収まり、既定のしきい値（`adequate_ratio=1.0`）で「適切」以上になることはそもそも一度もない。すなわちZ3は「既定のしきい値のままで既知の原因と矛盾しない」という結果（変化量0）を返した。12.12/12.13節で見つかった「唐突にoverkillへ切り替わる」不安定さは、**しきい値の選び方の問題ではなく、単一フレームで評価していたこと自体が原因**だったことが、この合成過程を通じて裏付けられたことになる。これは12.14節で導入した「スナップショット列＝CPDの箱列」という考え方——CPDの箱そのものが、ノイズに頑健な自然な時間積分の単位になっている——を、別の角度（減速演算子の安定化）から支持する結果でもある。
4. **合成の仕組み自体が非自明に働く例（架空のwhat-if）。** 「box#13は『弱い』ではなく厳密に『非常に弱い』でなければならない」という、既定のweak_ratio=0.5とは矛盾しない仮の追加知識に代えて、より厳しい仮の制約（ratio=0.55のケースが「非常に弱い」でなければならない、という架空の事例）を与えると、既定のweak_ratio=0.5と矛盾するため、Z3はweak_ratioを0.551へと、矛盾を解消する最小限だけ自動的に補正する。これにより、合成の仕組みが単に「何も変えない」だけでなく、実際に矛盾が生じた場合には最小限の補正を返すことを確認した。

**限界（正直に記録しておく）。** 現状はlog 0067という1本のログの、1種類の既知原因（「一貫して弱かった」という単調な制約）しか与えていないため、`adequate_ratio`と`weak_ratio`の間の境界、`overkill_ratio`の位置は、この制約だけでは実質的に拘束されていない（今回たまたま既定値のままで矛盾がなかっただけで、境界そのものを「発見」したわけではない）。しきい値合成が本当に意味を持つのは、複数のログ・複数の原因ラベル（例えばKSE2026論文の93件の衝突ログそれぞれについて、どの抽象値が主要因だったかをドメイン分析で確定させ、それらすべてを制約として与える）が揃ったときである。今後、他の衝突ログについても同様の原因分析を積み重ね、その結果をこのZ3合成に順次追加していくことで、しきい値がデータに基づいて引き締まっていくことが期待される。

実装は`logverify/abstract_cause.py`の`box_aggregated_deceleration_ratio`と、`logverify/synth_abstract_thresholds.py`（`synthesize_thresholds`、`python3 -m logverify.synth_abstract_thresholds`）。

### 12.16 複数ログ（衝突／非衝突）のラベルからのしきい値合成（v0.16）

12.15節の末尾に書いた限界——「1本のログ・1種類の既知原因だけでは境界を実質的に拘束できない」——に対し、ユーザーから的確な指摘があった。「要因（例えば速度）を与えると，衝突を起こしているログと，起こしていないログが与えられれば，それを区別するような抽象化は自動的に見つかるのではないですか？」

これは12.15節の方法（ドメイン分析による「原因」の人手ラベル付け）よりも優れている。**衝突の有無というログ単位のラベルは、ドメイン分析なしに、ログを集めるだけで自動的に手に入る**からである。

セッションの環境には、`TD-NI-AR-SD-N04-CI-*.json`という同一シナリオファミリー（NPCのカットイン）の6本のログがすでに存在していた（0030, 0032, 0035, 0047, 0067, 0076）。EGO・NPCの2D的な最近接度（`risk = max(|rx|/(車体長和), |ry|/(車体幅和))`、risk<1が衝突を意味する）で確認したところ、0067だけが実際に衝突しており、残り5本は衝突していなかった。同じシナリオの変奏で1本だけ衝突に至ったという、しきい値合成にとって理想的な教師データがすでに手元にあったことになる。

**方法。** `logverify/synth_thresholds_multilog.py`を実装した。各ログについて、NPCの車線変更開始フレームから最近接の直前フレーム（12.15節と同様、`required_deceleration_magnitude`が発散しないよう、縦方向距離がまだ正である最後のフレームを使う）までを1つの「箱」とみなし、その区間全体で平均化したachieved/requiredの減速比を、そのログ1本を代表する特徴量として計算する（12.15節の`box_aggregated_deceleration_ratio`のログ単位版）。その上で、Z3の`Optimize`に「衝突ログの比は、非衝突ログの比より必ず小さい」という分離制約を与え、分離可能な場合はマージンを最大化するしきい値を求める。

**結果。** 6本のログの減速比は次のようにきれいに分離した:

- 衝突ログ: 0067 (ratio=0.0042)
- 非衝突ログ: 0032 (0.397), 0047 (0.668), 0035 (1.771), 0076 (5.940), 0030 (8.757)

衝突ログの比(0.004)と、最も近い非衝突ログの比(0.397、0032)の間には約100倍の開きがあり、Z3はその中間(しきい値=0.2006、マージン=0.1964)を分離しきい値として合成した。これは12.12節以来使ってきた既定のしきい値(`weak_ratio=0.5`, `adequate_ratio=1.0`)よりもかなり厳しい(小さい)位置にある——既定のweak_ratio=0.5では、衝突していないログ0032(ratio=0.397)まで「弱い」と誤って分類してしまうところを、実データからの分離しきい値はそれを正しく「弱くない」側に置く。図は`out_gif/synth_thresholds_multilog.png`。

**12.15節との関係、および限界。** 12.15節の方法(既知の原因を人手で与える)と本節の方法(衝突/非衝突というログ単位のラベルだけを使う)は補完的である。前者は「なぜ」を説明する詳細なドメイン知識を必要とする代わりに、1本のログの中の時間発展(どの箱で悪化したか)まで教えてくれる。後者はログ単位の粗いラベルしか使わないが、人手のドメイン分析が一切不要で、ログを集めるだけでよい。ただし本節の結果にも限界がある: (1) 衝突ログが1本しかないため、その1点が外れ値である可能性を排除できない。(2) 6本すべてが同一シナリオファミリー(同じカットイン地点・車両サイズ)であり、他のシナリオファミリーに一般化できるかは未検証。(3) 「減速の十分性比」という1つの特徴量だけを見ており、横方向の余裕や予測信頼性等、他の抽象値との組み合わせでどう分離が変わるかは今後の課題。KSE2026論文にある93件の衝突ログ・残り339件の非衝突ログすべてを同じ枠組みに投入できれば、しきい値合成はより意味のある(データに基づいた)ものになるはずである。

実装は`logverify/synth_thresholds_multilog.py`（`log_level_deceleration_ratio`, `synthesize_separating_threshold`, `plot_separation`、`python3 -m logverify.synth_thresholds_multilog`）。

### 12.17 AJISAI全94本（cut-inシナリオ全体）での再検証——小標本の過学習という負の結果（v0.17）

12.16節末尾の限界に書いた「KSE2026論文にある93件の衝突ログ・残り339件の非衝突ログすべてを同じ枠組みに投入できれば」を、ユーザーからの「AJISAIにアクセスして、もう少し、規模の大きい実験はできますか？」という求めを受けて実行した。

**データ取得。** AJISAIデータセット（432トレース、KSE2026論文の参照[23]）はJAISTが公開しているBox共有フォルダ（`https://jstorage.box.com/s/1q19y57rztfpvh1t3u8fzschvxcxu1nu`）にホストされているが、クラウドサンドボックスのegress制限によりBoxドメインへは直接アクセスできない。そこでユーザーが自身のローカル計算機上でcut-inシナリオ全94本（`TD-NI-AR-SD-N04-CI-0001`〜`0094`、本体ログ+JAMAサイドカー）をダウンロードし、`Downloads/cutin/cutin/`に配置した。94本の生ログは合計約2.1GBあり、これをクラウドコンテナへ丸ごと転送するのは非効率なため、`logverify/synth_thresholds_multilog.py`の`log_level_deceleration_ratio`と完全に同一のロジックを移植したスタンドアロン版スクリプト（`compute_ratios.py`）をユーザーのローカル計算機上で実行し、ログ1本につき「減速の十分性比・衝突フラグ・最近接フレーム・カットイン開始フレーム」の4値だけを抽出した小さなJSON（94エントリ、約15KB）だけをクラウドコンテナへ転送するという設計にした。

**衝突判定。** AJISAIのメタデータ（`jama_index.json`等）には衝突フラグそのものが含まれていないため、12.16節と同じ`risk = max(|rx|/(車体長和), |ry|/(車体幅和))`（risk<1が衝突）を各ログについて独立に計算した。94本中13本が衝突と判定された（衝突率13.8%、KSE2026論文が報告するcut-inシナリオの衝突率16.0%(94本中15本)に近い——完全一致しない差は、論文側の衝突判定基準が本プロジェクトの2D矩形重なり判定と厳密には同一でない可能性を示唆するが、桁のオーダーは整合している）。

**結果：94本全体では単一の特徴量では分離できない。** `logverify/synth_thresholds_multilog_full.py`を実装し、94本のうち比が定義できた93本（衝突12本・非衝突81本、残り1本(`0002`)は比が定義できない特殊ケース）についてZ3で分離しきい値の合成を試みたところ、**UNSAT（分離不可能）**という結果になった。

具体的には:

- 衝突ログの比の範囲: [0.000142, 0.014446]
- 非衝突ログの比の範囲: [0.012048, 3.96×10^14]（このうち最小値0.012048の非衝突ログ`0044`が、衝突ログの最大値0.014446(`0093`)を下回っている）

つまり、94本中93本(比が定義できたログ)のうち92本については、6本のときと同じく「減速の十分性比」だけで衝突/非衝突がきれいに分離できる（衝突側が全て10^-2未満、非衝突側の大半が10^-2以上）。しかし非衝突ログ`0044`（ratio=0.012048）1本だけが、この境界のちょうど内側（衝突側の値域）に入り込んでおり、単一のしきい値による完全分離を妨げている。

**12.16節の結果は何だったのか。** これは「12.16節で見つかったきれいな分離は、1つの衝突例に対する過学習だった」ということを意味する、重要な負の結果である。6本のログ（衝突1本・非衝突5本）というデータ量では、Z3は「たまたま」分離可能なしきい値を見つけたが、母集団を代表するサンプルではなかった。**衝突/非衝突のラベルだけを使う12.16節の方法自体は依然として正しい**（12.15節のような人手のドメイン分析は不要という利点は変わらない）が、**分離可能性の結論はデータ量に強く依存する**ことが、規模を拡大したことで初めて明らかになった。これは「規模の大きい実験」を求めたユーザーの直感が正しかったことの実験的な裏付けでもある。

**外れ値としての`0044`。** 非衝突でありながら衝突ログ群とほぼ同じ比を示す`0044`は、それ自体が興味深い分析対象である——「危険な減速不足だったが、たまたま衝突を回避できた」ケース（ニアミス、near-miss）である可能性が高い。この種のログは、CPD箱列の可視化（12.14節）や原因分析演算子（12.15節）を個別に適用して詳しく調べる価値がある（未実施、今後の課題）。

**数値的な外れ値。** 非衝突ログの一部（例: `0074`、ratio≈1.47×10^14）で極端に巨大な比が現れた。これは`required_deceleration_magnitude`の分母（`distance_to_contact`）がゼロに近づく状況（NPCがカットインしてもEGOとの縦方向距離がほとんど詰まらなかった等）で、必要減速度がほぼ0に近づき、比が発散気味になる数値的アーティファクトであり、12.12/12.13節で見た問題の別の顔である。図(`out_gif/synth_thresholds_multilog_full.png`)では対数軸上でこれらの外れ値が右端に飛び出して見えるため、主要な分布域(10^-4〜10^2)に絞った拡大図(`out_gif/synth_thresholds_multilog_full_zoom.png`)も別途生成した。拡大図では、衝突ログ(赤×)のクラスタと非衝突ログ(緑○)のクラスタが`0044`を除いてほぼ完全に分離している様子が視覚的に確認できる。

**今後の課題。** (1) `0044`のようなニアミスログを個別分析し、境界事例で何が起きているかを理解する。(2) 「減速の十分性比」に加えて横方向の余裕（`classify_contact_margin`）や予測信頼性（`classify_prediction_reliability`）等、複数の特徴量を組み合わせた分離（例えば決定木や、複数のZ3制約の論理積・論理和）を試す。(3) cut-in以外のシナリオ（swerve: 衝突率34.6%、u-turn: 37.3%）でも同じ枠組みが有効かを検証する。

実装は`logverify/compute_ratios_standalone.py`(ユーザーのローカル計算機上で実行するスタンドアロン集計スクリプト。`python3 compute_ratios_standalone.py <ログディレクトリ> <出力.json>`)と`logverify/synth_thresholds_multilog_full.py`（`plot_separation_full`、`python3 -m logverify.synth_thresholds_multilog_full`）。

### 12.18 「多数のログの比較」ではなく「1本のログ＋あらかじめ用意した基準」による抽象化（v0.18）

12.16/12.17節の方法は、多数のログ（衝突／非衝突）を集め、その分布からZ3でしきい値を統計的に合成するというものであり、12.17節では「分離できるかどうかが手元のログの量と代表性に強く依存する」という限界が明らかになった。これに対しユーザーから、根本的に異なる2つの方針が提案された。

> 「多くのログを分析するのではなく、1つのログを分析するために抽象化するというのはどうでしょうか？…安全な振る舞いをするログをあらかじめ作成しておいて、それと比較するのはどうでしょうか？そのようなログの生成には、例えば、C&Cドライバモデルを使うのも良いと思います。…その他の方法としては，TTC等のcriticality metricsをあらかじめ一定間隔で抽象化しておいて、それに基づいてログを抽象化する手もあると思われます．」

**方法1: TTC (Time To Collision) による抽象化。** TTC = 縦方向の残り距離 ÷ 縦方向の接近速度を各フレームで計算し、業界で広く使われる目安（TTC<1.5秒: danger、1.5〜3秒: caution、それ以外: safe）で3値に抽象化する。この抽象値は、**他のログとの比較を一切必要とせず**、この1本のログの時間発展だけから直接求まる——ユーザーが提案した第2の方法そのものである。ログ0067（12.14〜12.17節で分析してきた衝突ログ）に適用したところ、カットイン区間（開始〜最近接）の55フレーム中40フレームがdanger、残りがsafeという結果になり（caution域はほぼ一瞬で通過し、safe→dangerへの急激な遷移が見られた）、TTCという単一の確立された基準だけで「危険だった」ことが直接読み取れた。

**方法2: IDM（Intelligent Driver Model）基準ドライバとの比較。** ユーザーが提案した「C&Cドライバモデル」に相当する具体的な実装として、確立された交通流モデルであるIDM (Treiber et al. 2000) を採用した。IDMは、追従車両の速度v・車間距離s・接近速度dvから、標準的な追従ドライバが出す加速度を計算する:

```
s*(v, dv) = s0 + max(0, v・T + v・dv / (2√(a_max・b)))
a_IDM = a_max・(1 - (v/v0)^δ - (s*/s)^2)
```

このa_IDMを「安全な基準ドライバならこの状況でこう振る舞う」という基準とみなし、実際にEgoが達成した加速度と比較する。12.15節の`classify_deceleration_adequacy`と同じ流儀で、achieved/required(=|actual|/|a_IDM|、a_IDMが負のときのみ定義)という比を計算した。

**結果と、既存の方法との整合性。** ログ0067にIDM基準を適用したところ、achieved/required比はカットイン区間を通じてほぼ0〜0.03という極めて低い値であり続けた（実際のEgo加速度はほぼ0、すなわちほとんど減速していない一方、IDM基準ドライバは終始強いブレーキを推奨し続けていた）。これは12.15〜12.17節で物理的な制動距離の式(v^2/2d)を使って得られた結果(0067のratio=0.0042〜0.0142、常に「非常に弱い」)と**桁のオーダーで一致しており**、独立した2つの基準(物理的な制動限界とIDMという確立された運転行動モデル)が同じ結論に達したことは、この結果の頑健性を裏付けている。

**発見: IDMもまた、接触直前で発散する。** クリップなしでa_IDMを計算すると、衝突直前には最小で-63592 m/s^2という非現実的な値に達した。これは(s*/s)^2の項が、車間距離sがゼロに近づくにつれて発散するためであり、**12.12/12.13節で見た「v^2/(2d)は単一フレーム評価に極めて敏感」という問題が、物理法則由来の基準だけでなく、確立された交通流モデル(IDM)由来の基準でも同じように起きる**ことを示す、重要な追加の知見である。実務上は、車両の物理的なブレーキ限界(本稿では-9 m/s^2、おおよそ1G)でクリップすることで対処した——恣意的な値ではなく、これも車両の物理的性能という既存の確立された基準である。

**12.16/12.17節との関係。** 本節の2つの方法は、どちらも「複数ログの統計的分布」ではなく「1本のログ＋あらかじめ用意した基準（TTCの業界標準閾値、IDMという確立された運転行動モデル）」から抽象化を導く点で共通しており、12.17節で明らかになった「分離可能性がデータ量に依存する」という問題を原理的に回避できる。特にTTCは、単一ログからでも即座に適用できる点で、12.16/12.17節よりも実用上はるかに軽量である。一方で、基準そのもの（TTCの閾値1.5秒・3秒、IDMのパラメータa_max, b, T, s0, δ）が「恣意的に選んだものではないか」という、9.5節以来プロジェクトが警戒してきた問題は、それらを業界標準・確立されたモデルに委ねることで軽減されてはいるが、ゼロにはならない。

**今後の課題。** (1) TTC・IDM比・12.15節の物理的比という3つの抽象値を、同一ログ上で並べて可視化し、それぞれがどの時点で「危険」を示すかの時間的な一致・不一致を調べる。(2) IDMのパラメータ（特にv0=希望速度）を、ドライバの個人差やシナリオごとに変えた場合に結果がどう変わるかの感度分析。(3) 12.17節で見つかったニアミスログ`0044`にも同じ2つの方法を適用し、衝突ログ0067との違い・類似を見る。

実装は`logverify/reference_model_comparison.py`（`compute_ttc`, `ttc_zone`, `idm_accel`, `python3 -m logverify.reference_model_comparison`）。図は`out_gif/reference_ttc_abstraction.png`（方法1）、`out_gif/reference_idm_comparison.png`（方法2）。

### 12.19 JAMA「有能で慎重な人間ドライバモデル」(C&Cモデル)による予防可能性判定（v0.19）

12.18節では、ユーザー提案の「C&Cドライバモデル」を、汎用の交通流モデルであるIDMとして実装した。これに対しユーザーから「C&Cドライバモデルは JAMA のものをつかってもらえますか？」との明示的な指定があった。

**C&Cとは何か。** 調査の結果、「C&C」は日本自動車工業会(JAMA)が「自動運転の安全性評価フレームワーク」(Automated Driving Safety Evaluation Framework)で定義する**Competent and Careful Human Driver Model**（有能で慎重な人間ドライバモデル）の略称であることが判明した(JAMA, Framework Ver.2.0, Section 2.3.3.1)。これはIDMのような汎用モデルとは異なり、**自動運転システムが安全とみなされるために超えるべき最低限の基準そのもの**としてJAMAが公式に策定したものであり、ユーザーが12.18節で提案した「安全な振る舞いをするログをあらかじめ作成しておいて、それと比較する」という発想に、まさに正面から応える基準である。

**モデルの定義**(フレームワークVer.2.0より):

- 知覚反応時間: 0.75秒(リスク知覚から制動力立ち上がりまでの遅れ)
- 最大減速度到達時間: 0.6秒(制動力立ち上がりから最大減速度まで)
- 最大減速度: 0.774G(日本の教習データ・NHTSA統計に基づく)
- カットインでの横方向リスク知覚境界: 1.8(NPCの最大横速度, m/s) × 0.4秒(リスク知覚時間) = 0.72m
- 縦方向リスク知覚境界: TTC = 2.0秒(UN規則ガイドライン)

フレームワーク文書は、この2つの境界（横方向0.72m、縦方向TTC2.0秒）の組み合わせ方や、減速度立ち上がりの正確な波形を明示していない。本プロジェクトでは「いずれか早い方でリスクが知覚される」(OR)、「0.6秒間で線形に0から0.774Gへ立ち上がる」という、文書の記述と矛盾しない最も単純な解釈を採用した。

**予防可能性の判定方法。** フレームワーク自身が「このモデルをシミュレーションプログラムに実装し、有能で慎重な人間ドライバにとって実際に回避可能な範囲を導出することで、安全基準を定義できる」(Section 2.3.3.1)と述べている手続きをそのまま実行した。すなわち: (1) 12.19節の2つの境界のいずれかでリスクが知覚されるフレームを特定する。(2) そのフレームでの実際のEgoの速度・位置を初期値として、C&Cモデルの減速度プロファイル（線形立ち上がり→0.774G維持）に従うEgoの反実仮想軌道をシミュレートする（NPCの軌道はEgoの挙動に依存しないと仮定——このプロジェクトのAJISAIログはすべて非対話的シナリオ再生であるため妥当な仮定）。(3) この反実仮想軌道と、実際のNPC軌道との間で接触（`risk<1`）が起きるかどうかを判定する。接触しなければ「予防可能(preventable)」、接触するなら「予防不可能(unpreventable)」と分類する。

**結果。** ログ0067に適用したところ、縦方向のTTC=2.0秒境界（横方向の0.72m境界より早く成立）で、最近接の5.7秒前にリスクが知覚されると判定された。この時点からC&Cモデルの反実仮想軌道をシミュレートしたところ、**最小2Dリスク値=4.02（実際のログの最小2Dリスク値0.917、すなわち衝突とは対照的に、余裕を持って安全）**という結果になり、本ログは「予防可能(preventable)」と判定された。図では、実際のログ（赤）がそのまま接触境界まで詰め寄っていくのに対し、C&Cモデルの反実仮想（青破線）は速やかに減速し距離を回復している様子が視覚的に確認できる。下段のグラフからは、実際のEgoの速度がリスク知覚から約4〜5秒後まで、ほとんど落ちていない(11m/s付近を維持)ことも分かる——これは12.15〜12.18節で一貫して見てきた「減速が非常に弱い」という結論と符合する。

**12.18節（IDM）との関係。** IDMとJAMA C&Cモデルは、着眼点が異なる: IDMは連続的な追従行動を近似する汎用モデルであり、「achieved/required比」という連続値の抽象化を与える。JAMA C&Cモデルは、規制・アセスメントの文脈で公式に確立された、離散的でより検証可能な基準であり、「予防可能／予防不可能」という2値の抽象化と、そこに至るまでの反実仮想軌道全体を与える。両者は独立に「実際の減速は非常に弱かった」という同じ結論に達しており、この結果の頑健性をさらに補強している。JAMA C&Cモデルの方が、規制・業界標準としての正当性という点で優れている一方、IDMは任意の追従状況に連続的に適用できる柔軟性を持つ、という使い分けが考えられる。

**限界と今後の課題。** (1) 2つのリスク知覚境界の組み合わせ方(OR)と、減速度の立ち上がり波形(線形)は、フレームワーク文書に明示がないため、本プロジェクトが妥当と判断した解釈である——将来的にJAMAへの確認や、フレームワークの後続バージョン(Ver.3.0, Ver.4.0)でより詳細な記述がないかの確認が望ましい。(2) NPCの軌道がEgoの挙動に依存しないという仮定は、このデータセットの性質上妥当だが、双方向のインタラクションが本質的なシナリオでは成立しない。(3) 12.17節のニアミスログ`0044`や、非衝突ログにも本判定を適用し、「衝突しなかったが予防可能マージンが小さい」ケースを識別できるかを検証する。

実装は`logverify/jama_cc_model.py`（`cc_deceleration_at`, `find_risk_perceived_frame`, `simulate_cc_reference`、`python3 -m logverify.jama_cc_model`）。図は`out_gif/jama_cc_model_comparison.png`。

参考文献: 日本自動車工業会(JAMA), "Automated Driving Safety Evaluation Framework" Ver.2.0, Section 2.3.3.1 "Competent and Careful Human Driver Model", https://www.jama.or.jp/english/reports/docs/Automated_Driving_Safety_Evaluation_Framework_Ver2.0.pdf

### 12.20 抽象化後のモデルをCPD箱列として可視化（v0.20）

ユーザーから「抽象化した後のログ，つまり，モデルが気になるので，そちらを可視化してください」との依頼があった。12.19節はTTCの時系列グラフと反実仮想の縦距離グラフという形で結果を示したが、これは12.13節の「実時間スイムレーン」に近い形式であり、12.14節で確立した「CPDの箱列そのものを描く」スナップショット列形式ではなかった。本節は、12.18/12.19節の抽象値を12.14節の形式に統合し、「抽象化後のモデル」を直接可視化する。

**拡張内容。** 12.14節の`ScenarioSnapshot`データクラスに、`ttc_label`（12.18節のTTCゾーン）と`rx_cc_ref`（12.19節のJAMA C&Cモデルの反実仮想における、その箱の代表時刻でのNPCとの縦方向距離）の2フィールドを追加した。`plot_scenario_snapshot_sequence`側では、`rx_cc_ref`が与えられている箱について、実際のNPC矩形と同じ横位置(dy0)・同じ大きさで、**青い破線のゴースト矩形**を反実仮想の縦位置(dx0)に重ねて描く。ラベル欄には、TTCラベルを最上段に追加した（12.12/12.15節の減速・予測・余裕ラベルは従来通り併記）。

**結果。** ログ0067にこの拡張版を適用したところ(`out_gif/jama_cc_scenario_snapshots.png`)、risk知覚後の各箱で、実際のNPC矩形（オレンジ、衝突箱では赤）とゴースト矩形（青破線）が時間とともにどんどん離れていく様子が直接視覚化された——箱#7(t=-1.18s)ではdx0の差はまだ小さいが、衝突箱#15(t=+2.19s、余裕ラベル「接触」・NPC矩形が赤)では、実際のNPCがEgoに重なって描かれる一方、ゴースト矩形は約50m先まで離れている。これは「抽象化した後のモデル」——実際の挙動と、JAMA公式基準による安全な反実仮想との乖離——を、1つの図の上で直接読み取れる形にしたものである。

**副次的な発見。** TTCラベルは、危険な接近中(box#7〜#13)は一貫して"danger"を示すが、衝突が実際に起きた箱#15以降では"safe"に戻ってしまう。これはTTCの定義（縦方向の残り距離÷接近速度）が「まだ接触していない、かつ接近中」の場合にしか意味を持たず、接触・すれ違い後は「もう近づいていない」ため機械的に安全側に分類されてしまうという、12.18節でも触れた性質である。CPD箱列という形式で可視化したことで、この「TTCは事後には無力である」という限界が、時系列グラフで見るよりもさらに直接的に（衝突箱のすぐ隣で"safe"ラベルが表示されるという形で）確認できた。

実装は`logverify/scenario_snapshot_diagram.py`（`ScenarioSnapshot.ttc_label`, `ScenarioSnapshot.rx_cc_ref`フィールドの追加、ゴースト矩形描画）と`logverify/demo_jama_cc_snapshot.py`（`python3 -m logverify.demo_jama_cc_snapshot`）。図は`out_gif/jama_cc_scenario_snapshots.png`。
